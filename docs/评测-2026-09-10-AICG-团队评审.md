## 缺陷清单

### P0

#### P0-1 `aicg check` 把未验证的治理状态报告为 `enforced: pass`

**描述**

`checkProject()` 仅以 `errors.length === 0` 得出一个 `pass`，随后同时赋给 `present`、`reachable` 和 `enforced`。它不读取 `docs/ai/acceptance-results.json`，也不要求任何负向探针、恢复证据或真实入口回放。

**证据**

- `src/modules/governance/checker.mjs:155-164`：三个维度共享同一个布尔值。
- `src/modules/governance/checker.mjs:171-175`：边界文字承认真实 Agent、项目行为、hook 和 OS 需要另行验证，但输出仍是 `enforced: pass`。
- `SKILL.md:334-338`、`README.md:95-105`、`references/product-architecture.md:63-71`：都把 `enforced` 定义为机器入口非零失败且已有负向证据。
- 临时空项目执行 `init --yes --no-assist` 后，未生成 `docs/ai/acceptance-results.json`；紧接着执行 `check --json` 仍返回：

```json
{
  "present": "pass",
  "reachable": "pass",
  "enforced": "pass",
  "realClientVerified": "unverified"
}
```

**影响**

这是 AICG 自己定义的典型 P0：“未验证条件显示成已满足”。它会让用户把结构完整误认为门禁已被负向证明，直接破坏产品最核心的证据可信度。

**建议**

1. `aicg check` 只报告它真实证明的结构维度；默认将 `enforced` 设为 `unverified`。
2. 只有 delivery checker 校验完整的 `acceptance-results.json`、契约覆盖率、真实入口、负向与恢复证据后，才允许 `enforced: pass`。
3. 加回归探针：初始化后没有 acceptance results 时，`present=pass`、`reachable=pass`、`enforced=unverified`。

#### P0-2 README 的公开 npm 安装入口安装到旧版，主流程中的八个命令不可用

**描述**

本地文档按 `0.2.0` 源码介绍完整命令集，但 README 首选安装方式没有固定版本；截至 2026-09-10，npm `latest` 仍为 `0.1.2`。

**证据**

- `README.md:153-180` 推荐 `npm exec --yes --package=ai-code-governance -- aicg init .`。
- `README.md:182-199` 随后要求使用 `assess`、`architecture`、`standards`、`team`、`harvest`、`complete`、`release-check`、`hook`。
- `package.json:2-4`：本地版本为 `0.2.0`。
- 实测 `npm view ai-code-governance version dist-tags --json` 返回 `latest: 0.1.2`；从 npm 安装 `0.1.2` 后的 `aicg --help` 仅包含 `init/check/sync/doctor`。当前元数据可由 [npm registry](https://registry.npmjs.org/ai-code-governance/latest) 复核。

**影响**

用户按首页官方路径安装后，大部分展示能力直接报未知命令；首次使用主流程中断。

**建议**

- 发布 `0.2.0` 前，把未发布命令明确标成“源码预览/next”；稳定版 Quick Start 只展示 npm `latest` 真正具备的能力。
- 发布后固定 README 示例的能力版本或增加自动发布一致性检查：README 命令表必须在 npm `latest` 安装包 smoke 中逐一存在。

### P1

#### P1-1 `doctor` 的契约与实现相反，Git/Agent 环境永远显示为 `not-probed`

- `references/initializer.md:19-33` 声明 doctor 检查 Node、Git、目录权限、Agent CLI；同文件 `:99-102` 要求环境命令由 doctor 单独诚实报告。
- `src/cli/commands/read-only.mjs:11-14` 与 `src/cli/commands/request.mjs:87-90` 都硬编码 `probeEnvironment: false`。
- `src/modules/repository/scanner.mjs:148-185` 的 Git/Agent 探测分支因此没有生产调用方；`src/modules/diagnostics/doctor.mjs:24-33` 的 `ok` 也不含 Git/Agent 条件。
- 当前机器 `git 2.50.1` 和 `codex-cli 0.151.0-alpha.7.1` 均存在，目标也是 Git 仓库，但 `doctor --json` 返回 `gitRoot: null`、Codex `not-probed`、整体 `ok: true`。

**建议**：显式 direct `doctor` 执行只读环境探测；聊天“修复治理框架”可继续使用安全的 no-probe 诊断模式，但字段和命令名必须区分。

#### P1-2 架构门禁可被多行 import 与根级实现静默绕过

- `test/architecture-boundaries.test.mjs:34-41` 用正则提取 import/export，无法解析多行 named import/export。
- `test/architecture-boundaries.test.mjs:76-107` 没有断言根级 `src/*.mjs` 必须是纯 re-export。
- `references/product-architecture.md:5-16` 明确要求跨模块只经对方 `index.mjs`，根级文件只做兼容 re-export。

在临时副本中加入以下两类违规，`node --test test/architecture-boundaries.test.mjs` 都以 0 退出：

```js
import {
  releaseAcceptance
} from "../release/acceptance.mjs";
```

```js
// src/new-implementation.mjs
export function shouldBeForbidden() { return true; }
```

**建议**：使用 Node AST/parser 或至少覆盖完整 ES module 语法；增加“根级实现必须失败”和“多行跨模块私有 import 必须失败”的定向负向测试。

#### P1-3 外部边界没有真正收口到 adapters

- `references/product-architecture.md:7-16` 要求 adapters 隔离文件系统、Git、npm、进程和 Agent 边界。
- 当前 `src/modules`、`src/kernel`、`src/cli` 中有 16 个文件直接 import `node:fs` 或 `node:child_process`。
- 代表性位置：`src/modules/repository/scanner.mjs:1-23`、`src/modules/completion/service.mjs:1-9`、`src/modules/release/repository-evidence.mjs:1-20`、`src/cli/commands/capabilities.mjs:1-8`、`src/kernel/config/constants.mjs:1-8`。
- 架构测试 `test/architecture-boundaries.test.mjs:81-84` 忽略非相对 import，所以不会发现此类边界违例。

**影响**：Git/npm/文件错误、超时与安全策略分散在多个模块，后续修复需要多点同步；“adapters 隔离”当前只是 stated。

**建议**：先抽取 Git、npm replay、repository filesystem ports，再由 modules 依赖 adapters 的公开入口；同时为 Node built-in import 建 allowlist 门禁。

#### P1-4 客户端范围 A2 的“必须显式选择”被 `--yes` 默认绕过

- `SKILL.md:47-50`、`references/interview-protocol.md:134-141` 明确规定 A2 永远是实质选择，不能自动推断。
- `references/initializer.md:35-45` 却允许 `--yes` 接受三款核心 Agent 默认值。
- `src/modules/governance/compiler.mjs:21-39` 的默认配置直接写入 `codex/claude-code/cursor`。

**影响**：最重要的授权边界在 Agent 流程中要求用户选择，在 CLI 流程中却可由通用 `--yes` 代替，并被决策账本包装为已记录配置。

**建议**：`--yes` 只能确认已显式给出的 `client_support.mode`；缺 A2 时以退出码 2 返回具体所需输入。

#### P1-5 跨平台证据相互矛盾，而且“当前”证据已经严重过期

- `README.md:124-132` 写 Windows/Linux 尚未实机执行；`README.md:368-370` 又写三 OS 的 Node 22/24 CI、smoke 和安装包均已跑通。
- `assets/registries/capability-pack-registry.json:21-38` 将三平台标为 `cli-ci-verified-node22-node24`，证据绑定提交 `75ebaba...`。
- 该提交到本报告评审快照 HEAD `18f4ea9` 之间已有 20 个提交、137 个文件变化（12,563 additions / 1,621 deletions），其中包括 CLI 模块化、完成/发布门禁和团队能力。
- `scripts/validate-skill.mjs:298-316` 只验证 URL/hash 格式，还硬编码三平台必须继续保持 verified；没有校验证据提交是否等于当前 candidate。

**影响**：旧 CI run 被错误解释成当前源码的三平台证据，且校验器反而阻止诚实降级。

**建议**：把 OS 证据绑定当前 package fingerprint 或 candidate commit；源码变化后自动降为 stale/unverified。README 由注册表生成，并拆分 CLI/package、真实 Agent 加载、目标项目 hook 三列。

#### P1-6 v3.0 `supported` 栈声明超过实际技术标准覆盖

- `README.md:113-122`、`assets/registries/capability-pack-registry.json:40-109` 将 React、Vue、Angular、Node、Java 标为 active + supported。
- `assets/registries/technical-standard-registry.json:39-260` 有 React、Mantine、NestJS、Fastify 等标准，但没有 Vue、Angular、Java、Express、Koa、Hapi 的专项标准。
- `scripts/validate-skill.mjs:451-500` 的必备标准集合没有要求 v3.0 支持矩阵完整覆盖。
- 临时项目实测 Vue、Angular、Spring/Java、Express 都能被识别为相应 stack，但 `aicg standards` 只返回通用 `software-design-and-verification`。

**影响**：“能识别栈”被展示成“已有细粒度当前标准能力”，与产品承诺不符。

**建议**：把 `detectionSupport`、`standardSkillCoverage`、`scenarioEvidence` 分开分级；Vue/Angular/Java/通用 Node 在补齐来源和细粒度 Skill 前降级为 unverified 或 partial。

#### P1-7 首页把“阻止旁路”写成现有能力，后文却承认尚未实现

- `README.md:29-32` 将 capability harvest 描述为会阻止后续绕过正典封装。
- `README.md:272-274` 说明 candidate/adopted 都不会自动封禁旁路。
- `references/continuous-skill-evolution.md:19-24` 将 consumer 解析和旁路门禁列为后续增强。

**建议**：首页改为“记录可复用能力并为旁路检查提供证据基础”；只有 `canonical-capability-reuse` 真实门禁落地后再使用“阻止”。

#### P1-8 `architecture` 自评误报，且建议没有采纳闭环

- `README.md:38-54` 已说明当前根级文件为兼容 facade、实现位于 modules。
- `src/modules/architecture/assessment.mjs:55-75` 仅按根文件数量、文件名和 400 行阈值判断，不识别纯 re-export 或既有架构文档。
- 实测 `aicg architecture . --json` 仍把 AICG 自身报告为 `flat-source-root`，并给出通用 `src/app + src/modules + src/shared` 蓝图。
- `src/cli/commands/init.mjs:47-51` 丢弃外部 `architecture` 配置，`:78-81` 直接派生内置决策；`assets/registries/architecture-profile-registry.json:3-27` 只有固定 profile。

**影响**：产品无法正确理解自己的兼容 facade；用户也不能把 assessment 的选择绑定 planHash 后交给 init/check。

**建议**：识别 re-export、现有 profile/ADR 与依赖证据；给 assessment 稳定 plan/profile ID，并增加显式 adopt 或允许已批准评估进入 init。

#### P1-9 首选的一次性 npm 调用与生成后的长期命令脱节

- `README.md:153-180` 首选不全局安装的 `npm exec --package=...`。
- `README.md:182-199` 和 `src/modules/governance/compiler.mjs:162-164,233-251,265-270` 的长期指令全部使用裸 `aicg`。

**影响**：即使 `0.2.0` 发布，用户完成一次性 init 后，新 shell/Agent 仍可能找不到后续命令。

**建议**：配置记录 `invocationMode + toolVersion`；生成固定版本 npm exec、项目本地 script，或经批准的全局安装入口，且 doctor 验证该入口。

#### P1-10 Brownfield 的核心差异化价值没有 CLI 接棒动作

- `README.md:3-5` 同时面向新建和遗留项目，并承诺当前标准与项目业务 Skill。
- `README.md:245-250`、`src/cli/commands/init.mjs:85-87` 对 existing/ambiguous 仓库禁止 AI assist。
- `src/modules/governance/compiler.mjs:306-310` 在无人工输入时只留下未确认业务不变量与待刷新标准。

安全拒绝直接修改既有业务代码是正确的，但典型 brownfield 首次运行只得到骨架，CLI 没有显式只读研究、候选 diff 和批准写入的下一步。

**建议**：增加只读 `enrich/plan`，只生成 `docs/ai` 候选，随后通过 planHash 批准；init 结束输出明确 CTA。

#### P1-11 B → C 的证据要求已经定义，但没有采集与晋级机器闭环

- `references/product-architecture.md:96-108` 要求两个真实项目、探针、平台矩阵、误判、逃生舱、门禁耗时与双 Owner 签署。
- `references/team-orchestration.md:61-77` 要求每次使用记录并形成匿名认证证据。
- `src/cli/help.mjs:1-35` 没有 trial/evidence/certification 记录或汇总命令。
- `test/real-scenarios/packaged-projects.test.mjs:185-347` 仅创建临时合成 greenfield/brownfield fixture，证据写在临时目录并在测试后删除；它不是两个真实客户项目的持久 evidence ledger。

**建议**：增加本地优先、可匿名化的 certification receipt schema 与 `evidence record/status/export`；绑定 pack/tool version、项目模式、OS、Agent、耗时、ack/误判和独立签署。产品 C 前先完成此闭环，而不是继续扩栈。

#### P1-12 中文/双语产物已定义，但 CLI 首次交互仍全英文

- `SKILL.md:53-60` 把中文、英文、双语访谈与治理产物列为 v3.0 能力。
- `src/cli/prompts.mjs:41-112` 和 `src/cli/help.mjs:1-35` 的首次问题、帮助与错误上下文全为英文；用户在完成多轮英文问题后才选择 artifact language。

**建议**：先选择或从 locale 推导交互语言，增加 `--lang zh-CN|en`；明确区分 `interactionLanguage` 与 `artifactLanguage`。

### P2

#### P2-1 根级兼容聚合器成为内部 service locator

`src/utils.mjs:1-14` 同时 re-export shared、kernel、filesystem adapter 和 process adapter；大量 modules 通过 `../../utils.mjs` 依赖它。边界测试无法为这个多层 shim 得出唯一身份，真实依赖方向被隐藏。

建议新内部代码直接依赖各层公开入口，根级 facade 只服务兼容消费者并加弃用计划。

#### P2-2 全仓扫描没有文件数量、单文件大小和总读取量上限

`src/modules/repository/scanner.mjs:148-157` 用 `maxDepth: Infinity` 遍历完整仓库；`src/modules/capabilities/detector.mjs:115-165` 同步读取并哈希源码。大型 monorepo、生成源码或超大 bundle 可能阻塞事件循环且占用无界内存。

建议增加默认 budget、可见截断状态、忽略策略和大型 fixture 性能测试。

#### P2-3 `team` 必填的业务描述不参与推荐语义

`src/modules/team/project-recommendation.mjs:99-124` 只验证并保留 `businessDescription`；`:370-390` 的推荐只依赖固定 signal、stage 和 package evidence。

建议把功能准确命名为“职责覆盖矩阵”，直接询问结构化信号；或由 Agent 层从描述提出候选信号，再由用户确认后进入确定式内核。

#### P2-4 单人最小档与发布人数硬门槛不匹配

`README.md:306-312` 把 minimal 定位给单人项目；`assets/policies/release-acceptance-policy.json:31-88` 即使 bugfix 也要求 1 工程师 + 1 独立架构师，且 override 不能降低。

建议把“项目完成门禁”和“组织/产品 C 发布认证”分开；单人可得到明确的 advisory/unverified 结果，高风险认证继续保持独立评审。

#### P2-5 工具版本、能力路线、证据等级三轴命名不清

`package.json:2-4` 为 `0.2.0`；`SKILL.md:53-60` 与 `references/product-architecture.md:110-119` 又称 v3.0/v3.1/v4 为版本路线。

建议统一字段与文案：`toolVersion`、`capabilityTrack`、`evidenceLevel`，首页同时展示映射。

#### P2-6 README 首次成功路径靠后且有两处过期维护文案

- README 共 412 行，安装到 `README.md:153` 才出现，Quick Start 到 `:182` 才出现；维护者源码架构反而在 `:38` 提前展开。
- `README.md:215-224` 示例需要三个环境变量，正文却写“缺少这两个变量”。
- `README.md:353-370` 用“第一条/第二条”和“两个注册表”解释六条命令和多类 registries/policy/contract。

建议首页前 60 行完成适用人群、稳定版能力、安装、三分钟成功路径与当前限制；状态与命令表尽量由机器源生成。

#### P2-7 产品 C 缺少明确 ICP、价值指标和 OSS/商业边界

`references/product-architecture.md:96-119` 的晋级标准几乎都是工程证据；`references/lifecycle.md:172-181` 的健康指标也集中在门禁、ack、规则和 harvest。仓库无法回答谁付费、首个可测成果是什么、Apache-2.0 核心与企业能力如何分界。

建议先选一个首要 ICP，并定义首次成功时间、减少返工、门禁误报/放弃率等价值指标；再决定认证能力包、控制平面、审计汇总和企业支持是否构成商业层。

## 亮点

- **写入安全边界扎实**：计划前像、symlink ancestor 复查、原子替换、事务回滚都有对应测试。
- **发布证据绑定较强**：candidate、Git evidence、脚本 hash、精确 replay approval、worktree 漂移与 package fingerprint 的防护完整。
- **概念模型有辨识度**：`present / reachable / enforced / real-client-verified`、单一正典、外部 workflow 单一 owner、candidate 不冒充 adopted，方向正确。
- **团队编排边界清楚**：探索、架构、实现、独立审计分权；角色按需激活且新增角色需要 Product Owner 审批。
- **测试面较广**：168 项覆盖初始化、结构、事务、链接安全、能力 harvest/promotion、完成门禁、发布 replay、团队建议、技术标准和打包场景。
- **文档大多数边界表达克制**：supported 不等于 certified、真实客户端与目标项目 hook 保持 unverified、brownfield 不隐式迁移。

## 建议的修复顺序

### 立即阻断（下一个公开发布前）

1. 修复 `enforced: pass` 误报，并加入无 acceptance results 的负向回归测试。
2. 对齐 npm `latest` 与 README；把公开安装包命令表纳入 installed-tarball smoke。
3. 将当前变更后的 Windows/Linux 证据降级或重跑 CI，并让证据绑定 candidate。

### 下一个迭代

4. 修复架构门禁多行 import/root implementation 盲区，并收口 adapters。
5. 统一 A2 客户端授权契约和 `doctor` 行为。
6. 拆分“栈识别”和“专项标准覆盖”，补齐 v3.0 或诚实降级。
7. 修复一次性安装后的长期调用入口、architecture adopt、brownfield enrich 三条用户链路。

### 产品 C 之前

8. 建立真实项目 evidence receipt 与晋级命令，先收集使用数据，不继续横向扩栈。
9. 明确单人/团队发布策略、中文 onboarding、版本三轴和 ICP/商业边界。

## 最终结论

**AICG 当前适合作为内部 B 阶段工具继续试运行，但不适合以现有 README 和证据状态对外宣称完整的 v3.0 supported 产品能力。**

底层工程质量并不差，问题集中在“证据语义和产品闭环”：测试很绿，但有些关键测试验证了错误的契约，或没有验证产品正在宣称的维度。最优策略不是继续增加功能和技术栈，而是先让 AICG 对自己做到三件事：

1. 不把未验证写成 enforced；
2. 安装到的版本与文档一致；
3. 每个支持声明都能追到当前 candidate、真实场景和可重放证据。
