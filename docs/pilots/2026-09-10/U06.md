## 独立 Review

- Reviewer 角色：Builder C 独立交叉 reviewer；覆盖 BA、后端、架构、安全、测试、可靠性、治理与 UX 视角。
- 主流程是否可运行：单进程演示可运行。独立 HTTP smoke 中，使用正确签名的 `POST /webhooks` 返回 `202 processed`，非法签名返回 `400`；但这只证明当前进程内行为，不能证明持久化幂等或生产副作用一致性。
- 测试是否真正覆盖成功 + 两条失败路径：4/4 通过，覆盖合法处理、非法签名、同进程并发合并和 event ID/payload 冲突，数量与断言有效。缺少进程重启、deliver 已产生副作用但记录未落盘、超大 body、畸形 JSON、时间窗重放和 secret 缺失测试。
- 业务不变量与权限边界：`#records` 与 `#inflight` 都是进程内 Map（`webhook-processor.mjs:6-7`）。独立重启探针用两个 processor 处理相同 event ID，两次均返回 `replayed=false` 且外部副作用计数为 `2`，所以“只产生一次外部副作用”不跨重启成立。`deliver()` 先执行、幂等记录后写入（`webhook-processor.mjs:31-35`），崩溃窗口也会重复副作用。
- 目录、模块和依赖方向：HTTP adapter 与 webhook processor 分离合理，单模块结构清晰；持久化 inbox/outbox、幂等 repository 和外部副作用 adapter 均缺失，无法建立跨实例一致性边界。
- 安全、可靠性与恢复：服务器在未配置环境变量时使用公开固定值 `development-only`（`server.mjs:4`）。独立 smoke 正是使用该默认值生成签名，并成功获得 HTTP `202`，因此任何调用者都能在默认部署中伪造 webhook。请求体无限累计（`server.mjs:7-8`），没有大小限制；签名也没有时间戳/允许窗口。该实现不足以称生产级。
- AICG 生成内容的准确性与噪音：`check`/`complete` 均退出 `0`，同时正确保留 `enforced=unverified` 与明确边界。问题是 complete 深度仍落到 `generic-unknown`，`domainConstraints` 为空，没有引导持久化幂等、原子副作用、secret fail-closed、body limit 或 replay window；仅靠四条单进程测试就能得到 `ok=true`，对中级用户形成过强的完成感。
- P0：① 应用/安全——缺少 `WEBHOOK_SECRET` 时采用公开默认 secret，可伪造任意 webhook（`server.mjs:4`），是生产发布阻断项；② AICG/治理——高风险 webhook 场景没有 secret fail-closed 或等价负向门禁，complete 未将该风险暴露为应用完成阻断。两项都需要回修，前者修应用，后者补 AICG 风险候选与验证 CTA。
- P1：① 应用/可靠性——内存幂等不跨重启/多实例，独立探针已复现重复副作用；② 应用/架构——副作用与幂等记录非原子，崩溃可导致重放；③ 应用/安全——无限请求体和无签名时间窗带来资源耗尽与重放风险；④ AICG/治理——complete 档未主动收集 webhook 的持久化、重放、外部副作用边界。这些问题共同否定生产级结论。
- P2：应用/API——合法签名但畸形 JSON 的解析异常会落入通用分支返回 `409`（`server.mjs:13`），应区分为 `400`；启动日志在自定义端口时仍打印 `3000`（`server.mjs:15`）。
- 问题归属：默认 secret、内存状态、非原子副作用、body/time-window 和错误映射属于应用；未识别 webhook 风险、未生成候选业务约束/负向验证属于 AICG；evidence 保持 unverified 属于正确的证据边界。
