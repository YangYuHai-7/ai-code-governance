## 独立 Review

- Reviewer 角色：独立 team-review（架构、业务分析、后端/全栈、安全、测试、API UX）；与 Builder C 分离。
- 复核命令与结果：2026-09-10 重跑 `npm test`、`aicg check`、`aicg complete --verify "npm run test"`、`aicg evidence status`，均 exit `0`；4/4 测试通过。治理继续报告 `enforced=unverified`、`realClientVerified=unverified`，receipt 为 `simulation-only`。
- 主流程是否可运行：类级 API 的 workspace—project—task 流程可运行，合法迁移和两个跨边界负向用例有效；HTTP API 没有成员加入路由，无法重放报告所述“成员加入后协作”的完整流程。更严重的是 HTTP 完全信任 body 中的 `actorId`：独立 smoke 未携带任何认证即可冒充 `alice` 在其 workspace 创建项目并返回 201。
- 测试是否真正覆盖成功 + 两条失败路径：4 条测试覆盖成功迁移、非成员创建任务、完成后回退、跨 workspace project 引用；但测试直接传可信 actorId，未覆盖 HTTP 身份绑定、成员邀请权限、空 memberId、并发 version 冲突、事件失败与持久化恢复，因此没有验证真正的 workspace 安全边界。
- 业务不变量与权限边界：TaskService 先校验 membership 再校验 project/workspace，顺序和跨 workspace 校验正确；但应用没有认证 principal，WorkspaceService 不保存 owner 角色，任何成员都能邀请其他人，且 memberId 不校验。独立类级 probe 证明 bob 可邀请 mallory；owner 还可把 `undefined` 加入成员，随后 `actorId=undefined` 可创建项目。
- 目录、模块和依赖方向：`app` 负责组装，workspaces/projects/tasks 分模块，shared EventBus 不依赖业务模块，是清晰亮点；但模块没有独立 public entrypoint，TaskService 直接持有 WorkspaceService/ProjectService 具体对象，跨模块契约未版本化，AICG 对 dependency direction/cohesion/single responsibility 仅 stated-only，无法阻止未来反向依赖。
- 安全、可靠性与恢复：无认证、无 owner/admin 角色、无持久化、无并发控制；version 字段只递增而不校验 expected version；状态写入与事件发布不原子，EventBus 没有 event id/version/time/delivery。所有状态在重启后丢失，不能支持生产协作或事件消费者。
- AICG 生成内容的准确性与噪音：AICG 准确记录 workspace membership、application service/events、状态迁移三条约束，并在 architecture profile 明示依赖方向等是 stated-only；但 complete 深度仍只有通用 backend Skill，没有把 workspace actor-resource authorization、role/invite policy、tenant isolation 和 module API contract 变成可执行门禁。这一诚实边界值得保留，但架构师 persona 的核心价值闭环未形成。
- 生产级判断：**否**。当前 HTTP 身份可伪造、成员流程缺失、邀请权限可提升，且数据和事件均不持久；只能作为内存领域模型示例。

### P0

- **HTTP 调用方可通过 body 伪造任意成员身份。** `/tmp/aicg-pilot-20260910/U10/app/src/app/server.mjs:17-23` 没有认证并直接转发 body；`projects/service.mjs:11-16` 与 `tasks/service.mjs:14-20` 仅按该 actorId 查 membership。独立 probe 未带 Authorization，声明 `actorId=alice` 即成功创建项目（201）。归属：应用。AICG 是否需回修：是，complete + workspace authorization 约束应要求 principal 来源与 actor-resource negative probe。建议：入口认证后覆盖/禁止 body actorId，service 接收可信 principal，并测试跨用户冒充。
- **HTTP 主协作流程缺少成员加入能力。** `CollaborationApp.addMember` 存在（`src/app/collaboration-app.mjs:15`），但 server 路由 `server.mjs:19-24` 没有暴露它；独立 probe 对 `/workspaces/{id}/members` 得到 404。因此新 workspace 除 owner 外无法通过 API 增加协作者。归属：应用/需求覆盖。AICG 是否需回修：否，属于主用户故事验收缺失。建议：实现带 owner/admin 授权的成员管理 API，并用真实 HTTP E2E 覆盖完整主流程。
- **成员服务允许权限提升和无效主体。** `/tmp/aicg-pilot-20260910/U10/app/src/modules/workspaces/service.mjs:18-23` 仅要求邀请者是普通成员，不验证 owner/admin，也不校验 memberId。独立 probe 证明 bob 可邀请 mallory，且加入 `undefined` 后无 actorId 的调用也能创建项目。归属：应用。AICG 是否需回修：是，workspace/tenant 场景应提示角色矩阵、主体有效性和邀请越权测试。建议：显式 owner/admin/member 模型、严格 ID 校验、邀请策略和审计；在修复前不得开放成员接口。

### P1

- **并发一致性和事件可靠性未建立。** `tasks/service.mjs:24-32` 虽维护 version，却不接收 expectedVersion；写 Map 后才发布事件。`shared/events/event-bus.mjs:1-9` 的事件没有 id、版本、时间或交付语义。归属：应用/架构。AICG 是否需回修：建议，协作/事件场景应提示 optimistic concurrency、transaction/outbox 和 event schema。建议：持久化 repository、CAS/version conflict、事务 outbox、版本化事件以及重放/失败恢复测试。
- **complete 架构门禁只检查目录放置。** `docs/ai/architecture-profile.json:53-62` 明确 dependency direction、cohesion、single responsibility 都是 stated-only；实际模块通过具体 service 对象相互调用且无模块 public entrypoint。归属：AICG + 应用架构。AICG 是否需回修：是。建议：complete 深度允许声明 module dependency graph/public APIs，并提供静态依赖检查；应用为每个模块建立显式入口/接口并限制内部路径访问。
- **所有业务数据仅驻留内存。** workspaces/projects/tasks 均为私有 Map，重启即丢失，无法验证跨实例 workspace 边界。归属：应用/使用边界。AICG 是否需回修：建议，在“团队协作”任务给出 persistence、tenant key、backup/restore 决策提示。建议：持久化并以 workspaceId 作为所有查询的强制分区键，加入跨租户数据库级测试。

### P2

- **错误契约和 UX 不稳定。** `/tmp/aicg-pilot-20260910/U10/app/src/app/server.mjs:26-28` 通过错误 message 正则决定 403，其余均 400 并原样返回内部消息，缺少稳定 code、request id 与 404/409 区分。归属：应用/API UX。建议：使用类型化错误和统一响应映射。
- **事件审计缺少邀请者。** `workspaces/service.mjs:22` 的 `workspace.member-added` 仅记录 memberId，不记录 actorId，无法追查谁授予访问权。归属：应用。建议：事件加入 actorId、workspaceId、eventId、occurredAt 和 schemaVersion。
