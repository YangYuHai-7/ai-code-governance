## 独立 Review

- Reviewer 角色：独立 team-review（业务分析师、架构师、后端/全栈、安全、测试、API UX）；与 Builder C 分离。
- 复核命令与结果：2026-09-10 在保留目录重跑 `npm test`、`npm exec -- aicg check . --json`、`npm exec -- aicg complete . --verify "npm run test" --json`、`npm exec -- aicg evidence status . --json`，四者 exit 均为 `0`；测试 4/4 通过。`check` 和 `complete` 继续报告 `enforced=unverified`、`realClientVerified=unverified`，receipt 继续为 `simulation-only`。
- 主流程是否可运行：最小内存态的“创建订阅—合法迁移—结算—幂等重放”可以运行；独立 HTTP 对抗 smoke 同时证明了未鉴权调用方可以取消订阅，并能把已取消订阅以任意 `1` 分金额结算为 `paid`。因此只能称可运行样例，不能称生产级账单系统。
- 测试是否真正覆盖成功 + 两条失败路径：现有 4 条测试覆盖一个成功路径和三类失败/边界（取消后非法激活、支付引用冲突、非正金额），测试实现真实有效；但没有覆盖结算所需订阅状态、服务端应付金额/币种、HTTP 鉴权、并发重放、存储或审计失败回滚。
- 业务不变量与权限边界：显式状态迁移表是正向实现；支付引用在单进程 Map 内具备幂等性。缺口是 `settleInvoice` 仅确认订阅存在，未要求 `active`，也没有 invoice 应付金额或 currency 的权威来源；HTTP API 没有认证/授权，`actorId` 完全取自请求体。
- 目录、模块和依赖方向：`server -> BillingService -> repository` 单向且 billing 模块内聚，repository 可注入，基础边界清楚；但只有内存实现，事件也是 service 私有数组，尚不存在持久化事务或可靠事件发布边界。AICG 对 dependency direction/cohesion/single responsibility 仍只做 `stated-only`。
- 安全、可靠性与恢复：所有写接口公开；请求 body 无大小上限；订阅、账单、幂等键和审计在进程退出后全部丢失；没有并发控制、唯一约束事务、outbox、重试或恢复验证。错误响应避免泄露未知 500 细节是亮点，但不足以抵消生产阻断项。
- AICG 生成内容的准确性与噪音：生成内容准确记录三条用户约束并诚实保持 unverified；`backend-node` Skill 仅要求读上下文、查版本、运行项目命令和标记未知项（`.agents/skills/backend-node/SKILL.md:10-14`），没有把 billing/支付场景转成金额来源、币种、鉴权、事务、并发幂等、审计可靠性检查。complete 档对高风险账单的增量价值主要仍来自人工输入。
- 生产级判断：**否**。至少先解决未鉴权写入、账单状态/金额权威来源、持久化事务和并发幂等，并形成独立安全与恢复证据。

## Builder 观察（供独立 Review 使用）

- 在 init 后添加正常的 `package.json` scripts 会使 manifest source 过期；如果用户直接按生成入口运行 check，必须先理解并执行一次 `aicg sync`。

- `backend-node v3.0` 仍为 `unverified`/`synthetic-only`，且 registry 明示 Express/Koa/Hapi 与 real-project evidence 缺口；账单事务、重试、并发和审计仅来自用户显式约束与实现判断。
