## 独立 Review

- Reviewer 角色：独立 team-review（安全、后端/全栈、架构、业务、测试、API UX）；与 Builder C 分离。
- 复核命令与结果：2026-09-10 重跑 `npm test`、`aicg check`、`aicg complete --verify "npm run test"`、`aicg evidence status`，均 exit `0`；4/4 测试通过，治理仍为 `enforced=unverified`、`realClientVerified=unverified`，receipt 仍为 `simulation-only`。
- 主流程是否可运行：AES-256-GCM 写入、按 scope 读取和非泄露鉴权消息在单进程内可运行；但独立 HTTP smoke 在不设置任何环境变量时，使用源码公开的 `local-writer` 成功写入（201），再用 `local-reader` 成功读取明文（200）。这直接阻断任何生产级凭据保管声明。
- 测试是否真正覆盖成功 + 两条失败路径：现有 4 条测试覆盖加密写读、未知 token、write-only token 和审计不含测试 secret，属于有效成功 + 负向覆盖；没有启动真实默认配置，因此漏掉最严重的默认凭据问题，也未测 key 缺失/轮换、密文篡改、超大请求、速率限制、持久化恢复和输入名称与 GET 路由的一致性。
- 业务不变量与权限边界：操作先 scope 鉴权、未知和 scope 不足均使用 `Access denied`，不在鉴权失败时探测资源，边界设计正确；但 scope 是进程内静态全局读/写权限，无资源范围、生命周期、吊销或身份系统绑定。默认 token 使该边界在实际 server 配置中失效。
- 目录、模块和依赖方向：`server -> vault service -> crypto/repository` 清楚，crypto 独立，repository 可注入；服务公开 `debugStoredRecord` 作为生产类 API，且存储、审计、身份数据均为内存实现。AICG 依赖方向仍为 stated-only。
- 安全、可靠性与恢复：密码算法、96-bit 随机 IV 和 GCM tag 选择合理；但默认认证凭据、启动时随机生成主密钥、无持久化/KMS/轮换、无 TLS 边界、无速率和 body 限制、审计不持久且未知 token 不留记录，不能形成凭据生命周期与事故恢复闭环。
- AICG 生成内容的准确性与噪音：AICG 将约束写入 `docs/ai/README.md:37-39` 并诚实标记证据边界；但 complete 档只生成通用 backend shell（`.agents/skills/backend-node/SKILL.md:10-14`），没有 security/threat-model capability，也没有对默认密钥、默认 token、KMS、transport、审计、rotation 和 secret-leak probes 的门禁。对本批最高风险 persona，治理价值明显不足。
- 生产级判断：**否**。公开默认 token 本身即 P0；即使修复，还需外部身份、KMS/轮换、持久化审计、传输安全、限流及恢复演练。

### P0

- **无配置启动时启用源码公开的读写 bearer token。** `/tmp/aicg-pilot-20260910/U09/app/src/app/server.mjs:5-10` 在环境变量缺失时回退到 `local-writer` / `local-reader`。独立真实 HTTP probe 用这两个值写入后读取到 `{"value":"secret-value"}`。归属：应用。AICG 是否需回修：是，高风险 secret-storage + complete 深度应检测/禁止生产路径默认凭据并要求 fail-closed configuration。建议：缺失 KMS key 或认证 provider 时拒绝启动；测试身份只能在显式 test harness 注入，绝不能存在运行时默认值。

### P1

- **密钥和数据生命周期不成立。** server 在缺少 `VAULT_KEY_BASE64` 时每次启动随机生成 key（`server.mjs:5-6`），repository 与 audit 又分别是内存 Map/数组（`repository.mjs:1-11`、`service.mjs:10`）；现在重启会丢失全部数据，未来换持久化 repository 后则可能留下无法解密的数据。归属：应用/使用边界。AICG 是否需回修：是，应提供 secret-storage 的 key source、rotation、backup/recovery 与 destructive-loss 检查。建议：KMS/HSM envelope encryption、key version、轮换/回滚流程和持久化恢复测试。
- **写入与读取的资源名契约不一致。** `service.mjs:20-27` 接受任意非空名称，HTTP GET 仅接受 `[A-Za-z0-9._-]+`（`server.mjs:28-29`）。独立 probe 实测 `space name` 写入返回 201，随后 URL 编码读取返回 404。归属：应用/API UX。AICG 是否需回修：否，属于应用契约测试缺失。建议：写入时执行与路由相同的规范化/验证，或对 URL segment 正确 decode 后统一校验。
- **生产安全边界缺少防滥用与可追责性。** `server.mjs:13-16` 无 body 上限；静态 token 无 expiry/rotation；未知 token 在 `service.mjs:49-55` 直接拒绝但不记录安全事件；审计只在内存。归属：应用/使用边界。AICG 是否需回修：是，security profile 应要求限流、请求上限、凭据轮换和失败审计策略。建议：接入真实 IdP、短期凭据、速率限制、持久化不可篡改审计与告警。
- **complete 深度未将敏感数据约束转成专项验证。** release policy 虽把 sensitive-data 标为独立安全 review，但 `check/complete` 仍可在没有 threat model 或安全 probe 的情况下 exit 0（状态仅 unverified）。归属：AICG。AICG 是否需回修：是。建议：在 high-risk domain 触发 security capability 与显式未满足清单，并要求默认凭据、日志泄漏、篡改、轮换和恢复的负向证据后才能形成更高交付声明。

### P2

- **密文没有绑定资源元数据。** `/tmp/aicg-pilot-20260910/U09/app/src/modules/vault/crypto.mjs:3-13` 未使用 GCM AAD 绑定 name/version；若 repository 层被篡改，合法密文可在记录间调换而不触发认证失败。归属：应用安全强化。建议：把稳定 resource id、tenant 与 key version 编码为 AAD，并覆盖 swap probe。
- **调试读取入口暴露存储记录。** `service.mjs:45-47` 的 `debugStoredRecord` 是生产类公开方法，虽当前只返回密文，也扩大误用面。归属：应用。建议：改为测试 fixture/repository 断言，不在业务 service 暴露调试接口。
