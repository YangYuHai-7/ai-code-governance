## 决策口径

- `now`：本轮优先整改项；下表同时标记当前 candidate 的实现状态，未满足的部分继续保留，不把局部实现写成完整验收。
- `next`：now 验收后再设计或试做，需新的范围确认，不构成本轮承诺。
- `later`：依赖外部环境、真实用户或更大能力建设，暂不排期。
- `reject`：明确不采用，因为会破坏证据边界、安全性或产品定位。

- 本文的“当前 candidate”特指整改后未发布包 SHA-256 `13f62358fcd986b1763dfc9e12e5d7f58e0bd3d4cb6023f98d286c26a84e275c`。U01–U10 使用的是整改前包 `9fbe94736ed2db7784f1be9160ecaec1a54fe415e10a278a14876d0ccc67580c`；整改后 candidate 仅完成仓库回归和 package smoke，未重跑十应用，更不是真人采用证据。

## Now

### N1 — Novice 单步行动引导与本地化

**当前状态：部分实现。** `doctor`、`assess`、`architecture` 已支持 `--locale zh-CN|en` 并输出行动指南、下一步与证据边界；help/onboarding 也已本地化，projectMode 明确为扫描形态而非用户确认的生命周期。尚未用真人证明 novice 能独立完成，且“完全不需要理解配置/术语”的端到端验收仍归 L3，不能标记为完成。

- 用户价值：让 U01/U02 不需要先理解 Git、brownfield、manifest、SemVer、negative probe、enforcement 等术语，也能知道“现在做什么、为什么、成功是什么”。
- 证据：[U01](U01.md) 在 zh-CN 下仍依赖 Builder 准备配置和翻译英文 JSON，违反协议的 novice 硬门槛；[U02](U02.md) 同样把“输出易懂”和“下一步”评为 3 分。
- 风险：翻译可能掩盖证据边界；过度简化可能让用户误以为 `ok=true` 等于可交付。
- 实现范围：为 human-readable 的 `doctor`、`assess`、`architecture`、`init` 增加 zh-CN 行动摘要；机器 JSON key 保持稳定。每一步最多突出一个推荐动作、一个原因和一个“不证明什么”；提供无需手写 JSON 的 novice prompt/preset，并把 lifecycle 冲突翻译成选择题。
- 验收标准：
  1. 在 U01 manifest-only fixture 上，zh-CN 非 JSON 流程从 doctor 到 init 不出现未解释的 Git/manifest/enforcement/negative probe 术语。
  2. 用户可以只通过选项完成 clients、greenfield、minimal、语言和 project-local 设置，不需要编辑 JSON。
  3. 每个成功输出包含明确下一条命令；每个警告包含修复动作与证据边界。
  4. snapshot 测试同时验证 zh-CN/英文 human output，JSON schema 与现有自动化调用兼容。
- 不在本项承诺：真人可用性结论。完成实现后仍需独立真人试点，归入 L3。

### N2 — Command/script 生命周期收敛

**当前状态：candidate 已实现。** 受管 `AGENTS.md` 不再复制易变的 package scripts；init 后新增 `test/start` 不会仅因脚本清单变化造成 manifest stale。`complete --verify "npm test"` 仅对安全等价形式归一为 `npm run test`，未知脚本、附加参数、管道和 shell 拼接继续拒绝；当前允许命令由只读 assessment 的 `actionGuide.allowedVerificationCommands` 给出。

- 用户价值：应用在 init 后正常增加 `start/test` script 时，不再经历与风险无关的 stale/sync 试错；等价安全命令不因字符串差异被拒绝。
- 证据：[U08](U08.md)、[U09](U09.md)、[U10](U10.md) 均在新增 scripts 后先因 AGENTS manifest source stale 失败，再手动 sync；三者的 `npm test` 被拒绝而 `npm run test` 通过。
- 风险：过度命令归一化可能扩大允许执行的 shell 范围；自动修改治理文件会违反显式 mutation 边界。
- 实现范围：只对已知安全等价形式做 canonicalization（首批限 `npm test` ↔ `npm run test`），不做任意 shell 等价推断；把 project script inventory drift 与 managed-governance drift 分开；当确需更新生成入口时给出一个原子、可预览的 sync CTA，不静默改文件。
- 验收标准：
  1. fixture 在 init 后新增 `test`/`start` scripts，不因无关 source hash 变化报告损坏的治理 manifest。
  2. discovered command 为 `npm run test` 时，`complete --verify "npm test"` 执行同一个 package script 并记录 canonical command。
  3. `npm run arbitrary`、带参数差异、管道或 shell 拼接仍被拒绝，安全 allowlist 不扩大。
  4. 真正修改 AGENTS/治理正典仍使 `check` fail closed，并给出精确修复命令。

### N3 — Business constraints routed verification 与生产就绪分层

**当前状态：candidate 基线已实现。** standard/complete 会生成 owner-confirmed 的 business-constraints registry、细粒度 Skill 及所选客户端适配器，约束以稳定 ID、原文和 SHA-256 绑定；minimal 只给升级 CTA。`complete` 已把结构结果与 `productionReadiness` 分开：存在已确认约束但证据缺失、过期或不完整时为 `blocked`，绑定完整也只到 `unverified / eligible-for-review`，永不自动称 production-ready。当前只校验结构化 evidence，不执行任意项目命令，也尚未实现带 owner/reason/expiry 的 waiver，因此本项是基线落地而非完整语义验收系统。

- 用户价值：把“约束被写进文档”升级为“知道由哪个 Skill/测试/人工决策验证”，同时避免把结构 `ok=true` 误读成生产就绪。
- 证据：[U01](U01.md) 的提醒/完成约束没有实现；[U05](U05.md) 取消只在类 API；[U07](U07.md) active membership 被忽略；[U08](U08.md) canceled 订阅可结算；[U10](U10.md) workspace 边界被伪造 actor 绕过。它们的最终 check/complete 仍均 exit `0`，虽然状态诚实保持 unverified。
- 风险：强行把自然语言自动转成规则会制造错误业务语义；把 production readiness 混入结构 check 会破坏现有清晰边界。
- 实现范围：给显式用户约束分配稳定 ID、source、owner、criticality、actor/resource/state/side-effect 元数据；生成可路由 business-constraint profile；维护 constraint → verification/waiver/unverified 映射。在 complete 摘要新增独立的 `productionReadiness` 状态（例如 `not-assessed`、`blocked`、`eligible-for-review`），保持 governance structure `ok` 的原语义。
- 验收标准：
  1. U01 “reminder triggers”或 U07 “active member only” fixture 若没有对应 verification/显式 waiver，structure check 可保持其真实结果，但 production readiness 必须为 `blocked` 并列出约束 ID。
  2. 每条 critical constraint 必须恰好映射到至少一个已执行证据或带 owner/reason/expiry 的 waiver；仅出现在 README 不算覆盖。
  3. 约束相关请求能路由到对应 business profile，且 profile 明示来源和仍未知的决策。
  4. complete 输出明确分开 structure、project command、business coverage、production readiness、real-client evidence，任何 unverified 不得显示为 enforced/certified。
  5. 不从代码关键词直接断言业务规则；低置信度推断只能生成待用户确认的问题。

### N4 — High-risk threat checklist 与负向证据门禁

**当前状态：部分实现。** 配置新增显式 `confirmedRiskSignals` 枚举，并为 authentication、authorization、payment、sensitive-data、external-side-effect、multi-tenancy、data-consistency、public-api 生成最低负向清单；不存在关键词自动推断。已确认风险但缺少当前约束绑定证据时 production readiness 为 `blocked`。尚未自动识别这些风险、自动执行六类真实攻击/并发探针或验证恢复证据，因此不能宣称原验收标准 1–2 已全部满足。

- 用户价值：当任务涉及凭据、webhook、支付、tenant/workspace authorization、持久化或外部副作用时，操作者无需独自想出最危险的失败模式。
- 证据：[U04](U04.md) 复现多实例 lost update；[U06](U06.md) 使用公开默认 webhook secret 且重启重复副作用；[U07](U07.md) 可伪造身份并忽略 inactive；[U08](U08.md) 未鉴权结算；[U09](U09.md) 默认 token 可取密；[U10](U10.md) actor spoof 与邀请扩权。
- 风险：静态信号会有误报；通用模板不能替代领域 threat model；若直接阻断所有开发命令会使 demo 无法迭代。
- 实现范围：基于显式任务/约束与已确认 surface 生成 threat candidates，由用户确认适用性；首批类别包括 fail-closed secret/key、可信 principal 来源、resource authorization、replay/time window、并发/唯一性、事务与外部副作用、body/速率预算、持久化/恢复、日志 secret。负向证据影响 production readiness，而不是把模拟探针升级为认证。
- 验收标准：
  1. 缺失 webhook secret、vault 默认 token、body actorId spoof、inactive membership、canceled invoice settlement、多实例 lost update 六类 fixture 均被对应 checklist/negative probe 标为 blocked。
  2. 修复 fixture 后，同一 probe 通过并记录 negative + recovery exit/diagnostic；证据与当前源码/配置 fingerprint 绑定。
  3. 对不适用项目允许显式 `not-applicable`，但必须记录 applicability reason；高风险项不能无理由跳过。
  4. simulated negative evidence 始终保持 simulation-only；没有独立真人/真实项目证据时不能进入 certified。

## Next

### X1 — 原生 surface 识别，而非立即承诺完整 native packs

- 用户价值：即使没有 React/Express 等框架依赖，也能识别 browser UI、`node:http`、JSON/file persistence、money/date 等真实 surface，并给出相称的候选检查。
- 证据：U01–U07 多数被归为 `generic-unknown`，独立 review 随后发现浏览器持久化、货币精度、a11y、请求预算、文件并发等重复缺口。
- 风险：启发式误判；“识别到”容易被误表述为“完整支持”。
- 实现范围：先设计 `surfaceSignals` 与 evidence level，输出候选 profile，不创建“supported/certified”声明。
- 验收标准：在固定 fixtures 上稳定区分 browser-ui、node-http、file-persistence；每个 signal 显示来源、置信度与 gap；无真实证据仍为 unverified。

### X2 — Surface 级验证编排

- 用户价值：让 UI/API 主用户故事必须从真实入口可达，避免只测内部类。
- 证据：U01 没有提醒触发，U05 没有取消 UI，U07/U10 API 不完整；现有单测均未发现。
- 风险：浏览器和服务依赖会增加环境成本与不稳定性。
- 实现范围：设计可选 HTTP contract、DOM/browser smoke profile，以及“未执行”状态；先提供项目命令编排，不宣称 AICG 自身验证全部 UX。
- 验收标准：fixture 中内部方法存在但 HTTP/UI 不可达时，surface story 标为 blocked；无浏览器环境时显示 unverified 而不是 pass。

### X3 — Module dependency 与 public API 声明/检查

- 用户价值：让 complete 深度对架构师真正检查依赖方向，而不只检查目录。
- 证据：[U10](U10.md) 的 dependency direction、cohesion、single responsibility 都是 stated-only，模块也没有独立 public entrypoint。
- 风险：不同语言/构建系统的 import graph 差异大，过早通用化会产生误报。
- 实现范围：先为 JS/TS 设计项目声明式 module graph 和内部路径 allowlist，再评估静态 verifier。
- 验收标准：fixture 的合法 app → modules → shared 通过，shared → domain 或跨模块内部路径依赖失败；未配置语言解析器时保持 stated-only。

## Later

### L1 — Native/framework capability packs

- 用户价值：提供更深的框架、API、浏览器和数据一致性指导。
- 风险：没有真实项目与版本证据时，扩包会制造虚假支持矩阵。
- 实现范围：在 X1/X2 有稳定 signal 与真实需求后逐个立项，不一次承诺所有 native packs。
- 验收标准：每个 pack 必须有版本范围、官方来源、正/负 fixture、真实项目证据边界和明确 evidence level；达到条件前保持 planned/unverified。

### L2 — 真实平台、跨 OS、hook/CI replay

- 用户价值：证明真实 Codex/其他已选客户端加载、Windows/Linux 行为和提交/CI 入口。
- 风险：依赖外部平台、账户、版本和执行环境，本轮 macOS simulation 无法替代。
- 实现范围：未来单独授权的 replay matrix；当前不承诺客户端或 OS 已支持。
- 验收标准：每个平台保存候选 fingerprint、真实入口、negative/recovery evidence 与运行链接/日志；过期证据降级为 stale。

### L3 — 真人与真实项目试点

- 用户价值：验证 novice 是否真能独立完成、团队是否愿意采用以及治理成本是否可接受。
- 风险：需要招募、隐私、同意与真实项目授权；模拟 persona 分数不能替代。
- 实现范围：另行设计真人协议和匿名真实项目 receipt，本轮不承诺人数、时间或结果。
- 验收标准：真实参与者明确同意，reviewer 身份与独立性可核验，receipt 为 real-project；simulation 不计入客户采用或认证分母。

## Reject

### R1 — 从 simulation/check/test 自动推导认证或生产级

- 理由：本轮 10/10 最终 check/complete 与 36/36 既有测试均通过，但生产级为 0/10；自动升级会直接制造错误信任。
- 保留规则：`simulated-persona` 永远是 `simulation-only`；结构、项目命令、真实客户端、业务覆盖、production readiness 和 certification 分栏展示。

### R2 — 无来源自动发明业务规则或自动生成高风险生产实现

- 理由：账单金额、tenant 角色、secret 生命周期等决策需要 owner 与项目证据；模型猜测不能成为正典。
- 保留规则：AICG 可以提出候选 threat/constraint 问题和模板，但采用必须记录 user/project source、owner 与 applicability；不得自动打开 hooks、CI、发布、外部 provider 或生产权限。

## 决策后的成功标准

本轮已完成 N2 与 N3 的 candidate 基线，N1/N4 仍为部分实现。下一阶段不是以“更多文件”或“更多 packs”为成功，而应补齐真人 novice 独立操作与真实 surface 负向探针：正常 script 演进不产生无意义试错；critical business constraints 有可路由证据映射且生产就绪单独判定；高风险默认配置和越权/一致性缺陷能从真实入口被明确拦截。即使全部实现，也只说明候选产品能力改善，仍不等于真实客户验证、真实平台支持或认证。
