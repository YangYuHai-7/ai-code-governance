# Documentation Publication Integrity Design

## Purpose

AICG must keep its documentation centralized, language-paired, release-complete, and mechanically bound to the product surfaces it describes. A release must fail before upload when required documentation is missing, misplaced, stale relative to a mapped product surface, inconsistent across languages, or absent from the npm package.

This design covers the AICG package repository itself. It does not change the documentation layout generated inside projects governed by AICG.

## Success Criteria

1. Human documentation has one canonical directory tree under `docs/`.
2. English and Simplified Chinese public documentation are explicit peers under `docs/public/`.
3. Root `README.md` is a generated npm/GitHub adapter, not an independently maintained source.
4. Root `SKILL.md` remains the required Agent Skill entrypoint and is classified separately from human documentation.
5. Every repository Markdown document is either registered in one documentation manifest or explicitly excluded as a required platform entrypoint.
6. Public language peers keep their shared structure, commands, machine identifiers, and release version synchronized.
7. Product surfaces that affect public documentation are mapped to the documents that own their explanation.
8. A release refuses to publish when a mapped product surface changes without a corresponding documentation change declaration and refreshed integrity baseline.
9. The npm tarball contains every document marked as release-required and contains no unregistered human documentation.
10. The checks are deterministic, offline, and usable from focused tests, validation, package smoke, and `prepublishOnly`.

## Non-Goals

- Proving that natural-language documentation is professionally or semantically correct.
- Translating arbitrary prose automatically.
- Moving generated target-project governance artifacts away from their existing `docs/ai` locations.
- Requiring every internal design or historical review to ship in the npm package.
- Adding symlinks or relying on filesystem links for documentation aliases.
- Making ordinary read-only AICG commands run the complete publication gate.

## Canonical Layout

```text
docs/
├── documentation-manifest.json
├── public/
│   ├── en/
│   │   └── README.md
│   └── zh-CN/
│       └── README.md
└── internal/
    ├── reference/
    ├── reviews/
    ├── specs/
    └── validation/

README.md
SKILL.md
```

The canonical English and Chinese project homes are `docs/public/en/README.md` and `docs/public/zh-CN/README.md`. The root `README.md` is generated byte-for-byte from the canonical English home with only path adaptation performed by a deterministic renderer. It remains at the root because npm and GitHub treat that location as the package landing page.

`SKILL.md` remains at the package root because Agent Skill discovery requires that entrypoint. It is registered as a platform entrypoint, validated for links and product-version claims, and excluded from the rule that ordinary human documentation must live below `docs/`.

Existing product reviews and optimization proposals currently stored directly under `docs/` move to `docs/internal/reviews/`. Existing reference and validation materials keep their current subtrees. No ordinary Markdown file may remain directly below `docs/` after migration.

## Documentation Manifest

`docs/documentation-manifest.json` is the single machine-readable inventory. It uses stable paths and contains:

- `schemaVersion`: manifest contract version.
- `packageVersion`: exact version expected from `package.json`.
- `entrypoints`: required root adapters such as `README.md` and `SKILL.md`.
- `documents`: every canonical human document with its audience, locale, publication status, and optional peer.
- `surfaceMappings`: product source patterns mapped to the documents responsible for explaining those surfaces.
- `integrityBaseline`: digests binding each mapped source group and its owning documents for the current release candidate.

Each document record includes:

```json
{
  "path": "docs/public/en/README.md",
  "kind": "public-home",
  "audience": "user",
  "locale": "en",
  "peer": "docs/public/zh-CN/README.md",
  "releaseRequired": true
}
```

Internal documents may omit `locale` and `peer` when they are implementation evidence rather than localized user guidance. They must still be registered and located under an allowed internal directory.

## Public Documentation Synchronization

Public language peers use stable synchronization markers already present in the project, such as `<!-- sync:quick-start -->`. Every synchronized section must exist exactly once in both peers and in the same order. The validator compares normalized machine-sensitive content within each paired section:

- fenced command blocks;
- inline commands and paths;
- headings represented by stable sync identifiers;
- package version references;
- supported Agent IDs, configuration values, and schema keys.

Human prose is allowed to differ by language. Machine-sensitive content is not translated or reordered unless the manifest explicitly declares a locale-specific exception. Exceptions must name the sync section and a reason; blanket file exceptions are not accepted.

The root README renderer transforms relative links from the English canonical path to root-relative links and otherwise preserves content. Validation regenerates the expected root README in memory and compares exact bytes. Publication never rewrites files implicitly; developers run the explicit documentation synchronization command before committing.

## Product Surface Mapping and Freshness

The manifest groups product surfaces by responsibility rather than mapping every source file independently. Initial groups include:

- CLI commands and help;
- configuration and guided onboarding;
- generated artifacts and repository layouts;
- professional testing workflow;
- release and publication behavior;
- supported Agents, stacks, and registries.

Each group declares source globs and at least one owning public document section. The integrity baseline records:

- a deterministic digest of the matched source paths and bytes;
- a deterministic digest of the owning canonical documents;
- the package version for which the pairing was reviewed.

If a source digest changes, validation reports the owning documents and refuses release until the documentation is deliberately reviewed and the baseline is refreshed. Refresh is an explicit command that requires both the mapped source group and its owning document digest to be recorded together. It does not claim semantic correctness; it records that the repository owner reviewed that mapping for the release candidate.

Changing only the baseline without changing documentation is allowed only with an explicit `noDocumentationChangeReason` for that surface group. Reasons are bounded non-empty prose stored in the manifest, visible in review, and cleared on the next mapped source change. This prevents silent checksum churn while allowing internal refactors that do not affect user behavior.

## Commands and Interfaces

One focused module owns documentation inventory, validation, rendering, baseline refresh, and package inspection. The initial public developer commands are npm scripts rather than new end-user AICG CLI commands:

```text
npm run docs:check
npm run docs:sync
npm run docs:baseline -- --surface <surface-id> [--no-doc-change-reason <reason>]
```

- `docs:check` is read-only and validates layout, inventory, peers, root adapter, version, links, surface freshness, and release-required paths.
- `docs:sync` writes only deterministic adapters such as root `README.md`; it does not translate prose or refresh integrity baselines.
- `docs:baseline` refreshes selected surface bindings after documentation review. It rejects unknown surfaces, missing documents, dirty or linked inputs, and unbounded reasons.

`validate:skill` invokes the read-only documentation check. `smoke:package` inspects the packed archive against the same manifest. `prepublishOnly` therefore fails before upload if either repository documentation or the npm artifact violates the contract.

## Publication Flow

```text
product or documentation change
        |
        v
update canonical docs under docs/
        |
        v
docs:sync -> deterministic root README adapter
        |
        v
docs:baseline -> explicit mapped-surface review record
        |
        v
docs:check -> repository integrity
        |
        v
test:full + validate + smoke + smoke:package
        |
        v
prepublish-check -> clean Git candidate + exact npm package shape
        |
        v
npm publish
```

No publication step silently repairs documentation. A dirty generated adapter or stale baseline is a failure with a precise remediation command.

## Failure Behavior

All documentation failures identify:

- the violated rule;
- the relevant document or product surface;
- the expected canonical location or peer;
- the command that can safely repair deterministic state, when one exists.

Examples include:

- `unregistered document: docs/new-guide.md`;
- `public document outside docs/public: GUIDE.md`;
- `missing locale peer for docs/public/en/README.md`;
- `root README differs from docs/public/en/README.md; run npm run docs:sync`;
- `release surface cli-commands changed; update its owning documentation and refresh the baseline`;
- `release-required document missing from npm package: docs/public/zh-CN/README.md`.

Repository validation must reject symbolic links, linked ancestors, duplicate document records, unsafe paths, missing files, and paths outside the package root.

## Migration

The migration is performed in one reviewed change:

1. Create the manifest and validation module with failing tests against the current scattered layout.
2. Move the English and Chinese public homes to `docs/public/en/` and `docs/public/zh-CN/`.
3. Move root-level reviews and optimization proposals into `docs/internal/reviews/`.
4. Update internal links and tests.
5. Generate the root README adapter from the canonical English home.
6. Add the initial product-surface mappings and integrity baseline.
7. Bind repository validation and package smoke to the manifest.
8. Correct the existing three-path/two-path wording inconsistency in both public languages.

Git history provides move traceability. No compatibility symlinks are created. Links in published documents use paths valid from their final package locations.

## Testing Strategy

Implementation follows test-driven development.

Focused tests cover:

- rejecting Markdown outside registered canonical locations;
- accepting the two required root platform entrypoints only;
- paired-section ordering and machine-token drift;
- deterministic root README rendering and link adaptation;
- package version drift;
- mapped source changes with updated docs;
- mapped source changes with a bounded no-documentation-change reason;
- stale or fabricated baseline updates;
- symbolic links, duplicate records, unsafe paths, and missing files;
- npm tarball inclusion of every release-required document;
- exclusion of unregistered human documentation from the tarball.

Migration verification runs focused documentation tests first, then `test:fast`, `test:full`, `validate`, `smoke`, `smoke:package`, `node scripts/prepublish-check.mjs`, and `npm pack --dry-run --ignore-scripts --json`.

## Evidence Boundary

Passing checks prove that documentation is centrally inventoried, structurally paired, mechanically synchronized for machine-sensitive content, deliberately reviewed against mapped product surfaces, and included in the npm package. They do not prove translation quality, factual completeness, professional review, or that every semantic behavior change was correctly classified. Those remain review responsibilities and must not be reported as machine-verified facts.
