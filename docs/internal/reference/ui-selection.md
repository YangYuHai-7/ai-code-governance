# UI 框架提案协议

UI 顾问只在**新项目**或用户显式要求重新评估时运行。遗留项目默认沿用现有设计系统和组件库；治理 skill 不把视觉重写伪装成框架建设。

## 先收集约束

至少确认：

| 维度 | 需要知道什么 |
| --- | --- |
| 产品类型 | 运营后台、SaaS、内容站、消费者产品、设计工具、移动/跨端 |
| 信息密度 | 表格与表单密集，还是内容与品牌表达优先 |
| 品牌自由度 | 接受 Material/企业设计语言，还是必须深度定制 |
| 无障碍 | 目标标准、键盘操作、读屏和高对比要求 |
| 渲染 | SPA、SSR、SSG、Web Components、微前端 |
| 主题 | 多品牌、暗色、设计 token、运行时换肤 |
| 团队 | 已有框架经验、设计资源、维护能力 |
| 组织约束 | 已有设计系统、许可证白名单、安全与供应链政策 |
| 平台 | macOS/Windows/Linux 浏览器矩阵，是否还要移动壳层 |

缺少关键约束时先问，不要按下载量或个人偏好直接排序。

## 候选池不是排行榜

以下名称用于启动调查，不是永久推荐。每次提案前都要核对目标项目兼容版本、官方维护状态、许可证、SSR/无障碍声明和组织政策。

| 前端栈 | 可调查的组件系统 | 可调查的低样式/Headless 路线 |
| --- | --- | --- |
| React | Material UI、Ant Design、Mantine、Chakra UI、Carbon | React Aria、Radix Primitives、项目自有 token/components |
| Vue | Vuetify、Element Plus、PrimeVue、Quasar | Reka UI、项目自有 token/components |
| Angular | Angular Material、PrimeNG、NG-ZORRO、Taiga UI | Angular CDK、项目自有 token/components |
| Svelte | Skeleton、Flowbite Svelte | Melt UI、项目自有 token/components |

“Tailwind CSS”是样式工具，不自动等于完整 UI 框架；“shadcn 风格分发组件”也与传统依赖型组件库有不同升级责任。提案时说明类别，不能把它们放在同一列只比较星标。

## 三候选方法

每次输出：

1. **首选**：最匹配主要约束，说明为什么。
2. **备选**：在一个明确条件变化时更合适。
3. **轻量方案**：更少依赖或 Headless/自建路线，说明团队需承担什么。
4. **不采用 UI 框架**：始终允许，尤其是品牌独特、组件面很小或已有设计系统时。

不要给三个高度相似的候选。候选应代表不同取舍，例如“完整企业组件”“高度可定制”“低依赖”。

## 评估维度

不使用看似精确但无证据的总分。逐项给 `strong / acceptable / weak / unknown`，并附来源：

| 维度 | 判定问题 |
| --- | --- |
| 技术兼容 | 匹配框架、元框架、SSR 和 TypeScript 要求吗？ |
| 产品匹配 | 组件密度和交互模式适合目标产品吗？ |
| 品牌与主题 | token、主题和深度定制代价如何？ |
| 无障碍 | 官方能力、项目实际验证和剩余人工测试是什么？ |
| 维护与生态 | 当前是否活跃，升级路径与破坏性变化如何？ |
| 许可证与供应链 | 当前许可证和依赖是否符合组织政策？ |
| 团队成本 | 团队学习、设计、测试和长期维护成本如何？ |
| 跨平台 | 声明浏览器和 OS 组合是否有真实验证？ |

维护状态与许可证是时效性事实。无法访问或验证官方来源时标 `unknown`，不凭记忆断言。

## 输出模板

```markdown
## UI 选择建议

约束：<产品类型、品牌、无障碍、SSR、团队、许可证、OS>

### 首选：<候选>
- 匹配：...
- 代价：...
- 证据：...
- 仍需验证：...

### 备选：<候选>
- 更适合当：...
- 代价：...

### 轻量：<候选或 Headless/自建>
- 获得：...
- 团队承担：...

### 不采用 UI 框架
- 可行条件：...

请选择一个，或修改约束后重新提案。
```

## 选择后的治理落点

用户确认后才生成候选规则，并继续从项目事实验证：

- 组件只能从哪个公共入口使用；
- token、主题和 CSS 所有权；
- 可访问性与响应式验证；
- 禁止混用哪些历史组件库；
- 视觉回归、浏览器和 OS 矩阵；
- 依赖升级由谁拥有。

这些规则属于目标项目，不回写为本 skill 的全局规则。

## 遗留项目例外

只有以下情况进入重新选型：

- 用户明确要求现代化评估；
- 现有库停止维护或存在不可接受风险，并有证据；
- 组织设计系统强制迁移；
- 当前库无法满足已确认的无障碍或平台要求。

即使满足，也先产出迁移 ADR、兼容策略和分阶段计划；不在治理框架安装过程中替换 UI 库。
