# Production-code governance acceptance

This is the acceptance contract for claiming that an AICG-generated framework can guide production code in a declared project and stack. A successful `aicg check` is structural evidence only. Report each requirement as `passed`, `failed`, or `unverified`; a missing result is `unverified`. Do not claim production-code readiness while any applicable requirement is failed or unverified.

1. **Framework baseline before code.** For each selected framework, generate a version-applicable implementation Skill with placement, correct and incorrect examples, error boundaries, and focused checks. A language-only choice must not silently select a framework. An unknown framework remains unverified.
2. **Unit-specific discovery.** Starting from every unit's Agent entrypoint, an unfamiliar developer can reach only the relevant baseline and adopted project Skills. A frontend change must not receive backend-only guidance, or vice versa. A missing entrypoint or required Skill fails this requirement.
3. **Existing-project overlay.** Retain current code. Discover layout and reusable-helper candidates from source and callers, compare return/error behavior and neighboring tests, and record conflicts. Repetition alone is not approval. Only an evidence-bound reviewed decision may adopt a project Skill; stale source invalidates the decision.
4. **Code boundaries.** Report the count of in-scope source files and files whose dependencies were actually inspected, by language. Zero inspected files or unsupported languages cannot pass a dependency-direction claim. A supported language must reject an injected cross-unit or private-module dependency and pass after recovery.
5. **Real task replay.** On a frozen candidate, give an unfamiliar implementer only generated entrypoints and a bounded feature and repair task. An independent reviewer checks code placement, approved reuse, API/data contracts, failure handling, and executed relevant tests. Record failures, assistance, and changed inputs; a simulation is not human acceptance.
6. **Four project shapes.** Replay a new single project, new multi-unit project, existing single project, and existing multi-unit project. Report each selected stack/version and operating system separately. An unsupported cell stays unverified; success in one shape does not transfer to another.
7. **Minimal design.** No required empty layers, plugin directories, new infrastructure, interface-per-class, or duplicate canonical Skills. A new abstraction needs a concrete second use or an evidenced boundary.
8. **One-sentence existing-project update.** In an already governed repository, the user says only “update the governance framework.” The Agent must inspect current code and ownership, refresh affected unit development docs and Skills, apply safe managed changes, and run the governance check without asking the user for CLI flags or a second approval of the same scope. Foreign ownership, deletion, migration, and missing owner decisions require a concrete choice. Record the actual Agent run; a registered phrase or dry-run alone does not pass.

The generated `acceptance-contract.json` includes negative and recovery probes for framework baseline, unit routing, existing-project convention review, and Skill-guided task replay. Those probes become evidence only after their real entrypoints run. AICG's review score still requires separate source-bound product results and independent review; file presence alone never supplies them.
