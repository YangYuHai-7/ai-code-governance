## 分级缺陷

### P0：根 `reports/`、`reviews/` 可静默吞掉真实产品源码

`LOCAL_OUTPUT_PREFIXES` 固定保留 `reviews/` 和 `reports/`；scanner 在事实识别前跳过它们，compiler 又把其中的新文件加入 `.gitignore`。architecture、surface、capability 和 risk fingerprint 因而都看不到这些源码。

独立复现 fixture：`/tmp/aicg-root-reports-product-probe.sn1RGP`。

```text
git status --short --ignored:
!! reports/new-production-route.mjs

aicg check --json:
ok=true
moduleGraph.status=passed
moduleGraph.inspectedFiles=[]
```

修改真实 `reports/service.mjs` 后，探针仍得到：

```text
productFingerprintChanged=false
riskFingerprintChanged=false
checkOk=true
```

代码位置：

- `src/kernel/config/constants.mjs:18`
- `src/modules/repository/scanner.mjs:169`
- `src/modules/governance/compiler.mjs:491`

影响：已有 reporting service、报表模块或后来放入这些目录的生产入口会绕过技术栈识别、surface 验证、module graph、风险证据漂移以及 Git 默认追踪。修复必须在占用目录前检查既有和已跟踪内容；扫描排除应绑定可信 ownership/manifest，不能只凭目录名；源码型或已跟踪文件必须阻断迁移或继续纳入治理。

### P1：未验证 manifest 可获得删除用户内容的所有权

checker 只做有限 schema 检查，没有验证 `generatedBy`、`templateVersion`、`toolVersion` 以及 expected ownership/kind/source 的精确一致性；后续 artifact plan 会信任 stale entry。

探针 `/tmp/aicg-foreign-manifest.VF3Vih13r10B` 使用 `generatedBy="Foreign Tool"`、`templateVersion=999`，把用户文件自报为 `gitignore-block`。`checkOkBeforeSync=true`、`plan.conflicts=[]`，应用后用户块 `KEEP-USER-BLOCK` 被删除。

建议：集中验证可信 manifest；只允许明确历史迁移清单中的 stale artifact；未知路径不得通过自报 ownership 获得替换或删除权限。

### P1：managed marker 子串碰撞可删除合法 `.gitignore` 规则

managed-block 使用未锚定 `indexOf` 查找 marker。合法 pattern 中只要包含 marker 文本，就可能被当作受管块整体替换。

探针 `/tmp/aicg-marker-collision.Jf77quhald8j`：

```text
literal# ai-code-governance:local-output:start
KEEP-USER-RULE
literal# ai-code-governance:local-output:end
```

结果为 `conflicts=[]`、`sentinelPreserved=false`。marker 必须只接受独占整行形式并兼容 CRLF；没有可信 manifest 的已有块只能在内容完全一致时接管，否则应 fail closed。

### P1：后置 negation 可解除敏感输出忽略，但 `check` 仍通过

管理块只校验自身 hash，不验证最终 Git ignore 语义。在块后追加：

```gitignore
!/reports/leak.txt
```

探针 `/tmp/aicg-gitignore-override.KvgLWZ45ZswV` 得到：

```text
git check-ignore -q reports/leak.txt => exit 1
aicg check => ok=true
```

这会让本地敏感报告重新进入 Git，而治理仍声称通过。`check` 应校验有效 ignore 语义，并阻止块后规则覆盖，或改用受管目录内的局部 `.gitignore`。

### P1：已有项目 onboarding 链路不能闭环到 `init`

内部评估员按 `doctor → assess → architecture` 操作时，流程停在尚不存在的 `docs/ai` surface declaration，没有直接给出 `aicg init` 命令，必须另查 help。首次使用的已有项目应从诊断结果直接得到下一条可复制执行的安全命令。

### P1：`zh-CN` guided flow 在关键决策阶段回退英文

中文 guided flow 的最终计划、批准和 lifecycle/boundary 内容回退为英文。对完全不懂技术的目标用户，这不是外观问题，而是是否能理解即将写入项目、谁能批准、哪些结论仍未验证的问题。

### P1：小白放错源码后的恢复指令不够可执行

内部 zero-tech evaluator 把 `src/todo.js` 放到错误位置后，`check` exit 1，但只得到抽象英文 placement advice，没有准确的目标目录、移动命令或再次验证命令。恢复路径应给出可复制命令、解释影响，并允许用户确认后执行。

### P1：真人试点缺少可审计的预注册载体

协议要求首场前冻结人数分层、任务、OS/client、主结果、帮助分类、停止标准、reviewer 分配和失效条件，但 external receipt 没有 preregistration、批准人、批准时间或摘要字段，无法证明这些决定不是看完结果后补写。

证据位置：`docs/validation/real-user-pilot-protocol.md:73`、`docs/validation/templates/external-evidence-receipt.json:6`。

### P1：真人 receipt 缺少结构化干预、负向恢复和 reviewer 审计

当前只有单一 `assistanceLevel`，没有逐次 moderator intervention；`negativeAndRecoveryEvidence`、`commands`、`verification`、`reviewers` 都是无 item schema 的数组，无法强制记录预期失败、实际诊断、失败 exit、恢复动作/exit、适用性和 reviewer independence。现有校验只保证空模板不能冒充证据，不验证已完成 receipt 的结构完整性。

### P1：真实项目授权和隐私留存字段不足

project 只有 `authorizationReferenceId`，缺少授权摘要、digest、scope、批准和到期时间；privacy 缺少 restricted-storage 分类、留存截止和删除记录。在补齐之前，不应采集真实项目或可识别参与者材料。

### P2：`.gitignore` drift 的推荐恢复命令会先失败一次

`check` 首先建议 `aicg sync .`，该命令 exit 2 后才提示 `sync --force`。这是可避免的失败步骤，应直接解释 drift、风险和需要确认的强制同步命令。

### P2：本地输出目录用途对小白不直观

`reviews/`、`reports/` 的用途主要出现在英文 AGENTS 文本和 `.gitignore` block。应提供中文 onboarding 摘要、README 或生成后的明确下一步，说明这些目录属于本地证据输出、不会默认提交，以及与项目自有同名目录冲突时怎么办。

### P2：真人体验评分与原十 persona 评分维度不一致

原试点有 7 个维度；真人协议/receipt 只有 installation、clarity、next step、recovery、confidence 五项，缺少“规则是否帮助应用实现”和“治理成本是否与风险匹配”，后续分数无法直接比较。

### P2：receipt 缺少 eligibility 的显式机器字段

协议允许真实项目 receipt 经两名独立 reviewer 后进入 `eligible-for-human-certification-review`，模板 claims 却只有 `certified`，不能机器记录“具备送审资格但尚未认证”。

## 真人试点启动条件与最小矩阵

真人测试不能由 AI 自行招募、同意或代签。启动前至少需要：

1. Product Owner 书面批准研究目的、声明边界、任务、分层、停止标准和评分问卷。
2. 招募 10 名不同的真实成年人并逐人取得知情同意；Agent/persona 不计人数。
3. 如使用真实项目，取得项目所有者对具体任务、数据采集和负向探针的授权。
4. 指定真实的 coordinator、moderator、privacy custodian、implementation owner、Project Manager 和 independent reviewer，并披露冲突。
5. 建立受控存储、访问名单、身份映射、留存/删除期限和 withdrawal channel。
6. 修复本报告 P0 和真人证据 P1 后，重新冻结候选，并由 moderator 与 reviewer 独立复算 digest。

最小定向样本建议如下；它可以验证可用性，不能据此推断市场采用：

| 分层 | 对应任务 | 真人数/会话 | 推荐项目 |
| --- | --- | ---: | --- |
| 非技术/轻技术 | U01–U02 | 2 人 / 2 场 | 消毒后的 synthetic fixture |
| 初级开发 | U03–U04 | 2 人 / 2 场 | synthetic fixture |
| 中级开发 | U05–U07 | 3 人 / 3 场 | synthetic fixture；真实项目另行授权 |
| 高级/高风险 | U08–U10 | 3 人 / 3 场 | disposable synthetic fixture 优先 |

每场先记录 unassisted 首次尝试；发生帮助后逐次记录干预并标记 assisted；执行一个预注册主任务和一个安全 negative/recovery 场景；使用同一冻结候选和预声明 client/OS/runtime；由非 moderator、非实现负责人、非项目经理的 reviewer 审查；withdrawn 会话立即从人数、评分、引语和声明中排除。
