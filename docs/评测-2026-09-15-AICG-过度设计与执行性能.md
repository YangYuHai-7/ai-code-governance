# 评测 2026-09-15 AICG 过度设计与执行性能

## 执行汇总

- 评审范围：`SKILL.md`、十二层/十二原则、初始化与生成器、上下文路由、扫描/检查器、CLI 入口、测试脚本，以及当前源码生成的临时项目。
- 评审方式：架构、AI 上下文、全栈性能、业务成本、测试与 CLI UX 六个视角交叉复核；未修改产品代码。
- 结论：**存在过度设计，且已经会增加 Agent 的阅读与流程成本；但当前 `aicg check/complete` 的纯机器执行速度并不慢。** 主要风险不是 CPU，而是最小档产物过多、普通任务常驻指令过重、模糊请求默认升级到完整模式，以及默认命令可能重复走 npm 包解析。
- 缺陷分级：P0 0 项、P1 4 项、P2 3 项。
- 当前回归：`npm test -- --test-reporter=dot` exit `0`，总耗时 `135.29s`；`npm run test:architecture -- --test-reporter=dot` 为 4/4 passed，`0.29s`。

## 实测数据

### 生成物规模

使用当前源码生成 greenfield、React + Node、三个内建客户端、`project-local`、不启用 hooks/CI/AI assist 的临时项目：

| 深度 | 项目文件数 | 总字节 | 总行数 | `check` 平均 | `complete` 平均 |
| --- | ---: | ---: | ---: | ---: | ---: |
| minimal | 21 | 65,205 | 1,151 | 87.4ms | 87.2ms |
| standard | 30 | 82,061 | 1,556 | 99.7ms | 101.5ms |
| complete | 37 | 87,946 | 1,678 | 101.5ms | 102.6ms |

更贴近 guided 默认选择的 Codex-only + generic-unknown minimal 项目仍有 **19 个文件、63,710 bytes**。历史 U01 试点曾记录 minimal 生成 15 个治理文件，并评价“对单人小应用仍偏多”（`docs/pilots/2026-09-10/U01.md:17-18,47`）；当前基线又无条件增加了 `.gitignore`、`reviews/` 和 `reports/` 等产物。

### Agent 启动阅读量

按 `default_start` 与 implementation profile 的 required 文件去重计算：

| 深度 | 普通实现启动文件 | 总字节 | 粗略 token 量（bytes / 4） |
| --- | ---: | ---: | ---: |
| minimal | 4 | 6,445 | 约 1,611 |
| standard | 7 | 10,892 | 约 2,723 |
| complete | 7 | 10,892 | 约 2,723 |

这还没有计算根据 `technical-standards.json` 继续加载具体 Skill 的内容。它不会压垮上下文窗口，但会让每次小修复在第一次编辑前先消耗固定阅读与决策步骤。

### 扫描规模

在已生成 minimal 项目中追加文件后实测：

| 仓库规模 | 内容 | `check` 平均 |
| --- | --- | ---: |
| 1,000 文件 | 512-byte 非源码文件 | 156.7ms |
| 10,000 文件 | 512-byte 非源码文件 | 651.3ms |
| 1,000 文件 | 小型 JS 源码 | 163.9ms |
| 5,000 文件 | 小型 JS 源码 | 399.2ms |
| 10,000 文件 | 小型 JS 源码 | 678.0ms |

当前扫描器有 50,000 文件、20,000 目录、100,000 entry 和单文件 2 MiB 的明确预算（`src/modules/repository/scanner.mjs:20-26`），所以本轮没有把全仓扫描判为当前性能缺陷。但它只全局忽略 `.git` 和 `node_modules`（`src/modules/repository/scanner.mjs:169-177`），大型仓库仍需要持续性能基线。

## 多角色判断

### 架构师

- 单一正典、适配器和可失败检查器三件套是必要复杂度，不应删除。
- 十二层作为参考架构可以保留，但当前“模糊请求默认完整模式”和“minimal 仍生成多层产物”破坏了按风险渐进启用的边界。
- `complete` 与 `standard` 的常驻阅读量相同，但 complete 的实际能力又依赖额外 feature 开关，档位语义不够清晰。

### AI 专家

- 最大延迟来自上下文路由，而非 Node CLI。standard/complete 把技术标准清单和 capability evolution 放进 `default_start`，同时在 `AGENTS.md` 与 always rule 重复提示 release、harvest、sync、hook 与报告目录。
- 对模型而言，过多同级“必须”会降低真正关键约束的显著性。普通两行修复和发布任务看到相近的常驻仪式，容易产生过度执行或选择性忽略。

### 全栈工程师

- 小项目 `check/complete` 约 0.1 秒，1 万源码文件约 0.68 秒，检查器不是当前慢点。
- AICG 自身完整回归 135.29 秒，适合作为合并/发布门禁，不适合作为每个微小实现循环的唯一反馈入口。现有 architecture 定向测试只需 0.29 秒，说明可以建立更清晰的 fast/full 分层。

### BA / 产品

- 用户选择 minimal 的核心预期是“少文件、少概念、马上开始编码”；19 个文件、验收契约、发布策略、surface profiles、decision ledger 与两个本地工作区不符合这个心智模型。
- “治理框架”一句话就默认 L0–L11，会把尚未证明价值的复杂度一次性交给单人或小项目，增加首次成功时间。

### 测试与 CLI UX

- 当前测试对安全边界、幂等、漂移和负向探针覆盖较强，这是亮点。
- 尚缺“生成物预算”和“Agent 完成真实小任务的时间/工具调用数”回归，因此新增文件或常驻指令不会让测试失败。
- `npm-exec-pinned` 是非 guided 默认调用方式；每个治理命令都可能先经过 npm package 解析。现有本地性能数据使用 `project-local`，不能证明默认远程/缓存路径稳定快速。

## 缺陷清单

### P0

- 无。当前没有证据表明生成项目因治理检查器而不可用或普遍阻断。

### P1

#### P1-1 minimal 档位与生成物契约不一致

**现象**：`SKILL.md:170-189` 明确定义 minimal 为 L0 + L1 + L8，但 `src/modules/governance/compiler.mjs:491-527` 无条件生成 context map、verification profiles、anti-patterns、架构 profile/rule、decision ledger、bootstrap prompt、surface verification contract、release policy、`reviews/`、`reports/` 等。Codex-only minimal 实测为 19 文件、63.7 KB。

**风险**：单人小项目的 Git 噪音、理解成本和维护表面积显著高于“最小”承诺；用户可能因此整体绕过治理。

**修复方向**：把 minimal 收敛到配置/manifest、共享入口、常驻规则和一个检查入口；context routing、架构 policy、anti-patterns、verification profiles 进入 standard；release/surface evidence 和本地评审工作区改为显式 feature 或首次使用时惰性生成。建议设硬预算：Codex-only minimal 不超过 10 个文件，常驻启动阅读不超过 1,000–1,500 tokens。

#### P1-2 模糊请求默认完整模式，违反风险比例原则

**现象**：`SKILL.md:36-51` 把“建立治理”等短语默认映射到 L0–L11 自动完整模式；同文件 `SKILL.md:151-164` 又要求门禁与风险成比例、使用最轻仪式。

**风险**：对单人、短生命周期或低风险仓库，Agent 会执行技术标准检索、能力工厂、任务运行时、成长闭环和独立审计等完整流程，首次落地时间可能远高于实际开发时间。

**修复方向**：无明确档位时默认 standard；仅在“多客户端 + 长任务/跨会话 + 高风险边界 + 团队强制”满足明确阈值时推荐 complete，并由用户确认。minimal 作为 novice/guided 默认，standard 作为专业默认，complete 必须显式选择或由风险信号升级。

#### P1-3 普通任务的常驻路由包含发布与能力演进噪音

**现象**：`src/modules/governance/compiler.mjs:181-215,227-251` 把 technical standards、capability evolution、harvest、hook、reports 和 release 都写入共享入口或 always rule；`src/modules/governance/compiler.mjs:275-328` 又已经提供 implementation/review/release profiles。standard/complete 普通实现启动阅读实测约 2.7k tokens。

**风险**：每次小修复都支付发布与治理演进的认知成本；重复规则降低真正任务约束的注意力权重。

**修复方向**：共享入口只保留正典位置、最小加载规则、保护用户改动、一次完成门禁指针。release 只由 release profile 加载；harvest 只在行为变更收尾 profile 加载；technical standards 与 capability catalog 从 `default_start` 移到 implementation profile 的按技术/路径触发项。

#### P1-4 非 guided 默认命令存在 npm 解析延迟与不确定性

**现象**：`src/modules/governance/compiler.mjs:24-28,31-50` 将 `npm-exec-pinned` 设为默认，并把治理命令渲染成 `npm exec --yes --package=...`。guided 流程反而把 `project-local` 标为推荐。

**风险**：普通 `check/complete` 的核心逻辑虽然约 0.1 秒，但默认包装层可能引入 npm 缓存检查、包解析或网络波动；在离线环境还会把快速本地门禁变成不可用入口。本轮 0.1 秒数据不覆盖该默认路径。

**修复方向**：统一默认到 project-local；初始化时检测未安装则给一次明确安装/固定版本步骤。`npm-exec-pinned` 保留为 bootstrap/临时模式，不应成为每次门禁的默认执行路径。

### P2

#### P2-1 客户端副本与根级工作区继续放大表面积

complete + 三客户端实测 37 个文件，其中 10 个是客户端适配器；每个 canonical Skill 可能再复制到 `.agents/` 与 `.claude/`。`src/modules/governance/compiler.mjs:491-511,582-602` 还无条件或按客户端增加根级文件与副本。哈希与 manifest 能防漂移，但不能消除浏览、审查和 Git 状态噪音。

建议只为用户明确选择且确有原生发现需求的客户端生成副本；`reviews/`、`reports/` 改为首次写入时创建，或至少从 minimal 基线移除。

#### P2-2 AICG 自身完整回归过重，缺少默认快速反馈套件

`package.json:23-32` 的 `npm test` 直接运行全部 Node tests；本机实测 135.29 秒，而 architecture 定向测试仅 0.29 秒。完整套件用于 prepublish 是合理的，但开发者缺少一个覆盖核心编译/生成/检查路径且可在数秒内完成的默认 fast suite。

建议增加 `test:fast`，覆盖 config → artifacts → apply → check 的关键 happy/negative paths；完整跨进程、打包、发布证据和真实场景保留给 `test:full` / prepublish。

#### P2-3 缺少性能与 Agent 行为预算门禁

当前回归大量验证正确性，但没有对以下指标设失败阈值：各档生成文件数、default_start 字节/token、单任务必读文件数、1k/10k/50k 文件检查 p95、首次编辑前工具调用数、简单 bug 的端到端完成时间。

建议新增固定 fixture 性能基线，并允许 CI 使用宽松抗抖动阈值；Agent 侧至少回放三种任务：只读问答、单文件 bugfix、中等 feature。没有这些门禁，框架会在每次“多加一个安全文件/规则”时缓慢膨胀而不触发任何测试失败。

## 亮点

- `SKILL.md:151-164` 已明确写出最小上下文、风险比例和最轻仪式，方向正确。
- 生成入口明确禁止普通对话轮次反复跑门禁（`src/modules/governance/compiler.mjs:210-212,248-249`）。
- 项目完成与组织发布认证已经分离，避免单人项目被独立 reviewer 人数直接卡死。
- 扫描预算已有限制，当前 10,000 个小型源码文件的结构检查仍低于 0.7 秒。
- hooks、CI 和外部 workflow 默认关闭，没有把高副作用集成静默装进项目。

## 建议的收敛顺序

1. 先修 P1-3：把 release/harvest/standards 从常驻链路移到任务 profile；这是风险最低、收益最直接的减负。
2. 再修 P1-1：重新定义并测试 minimal artifact allowlist，目标是文件数减半。
3. 将默认自动完整模式改为 standard + 风险升级，并统一 `project-local` 调用默认。
4. 最后增加 artifact/context/performance budget 测试，防止以后再次膨胀。

## 最终判断

当前 AICG 不是“运行器慢”，而是“治理层比项目风险更容易先膨胀”。如果保持 project-local 且只在交付末尾跑一次门禁，机器耗时基本可忽略；真正会让 Agent 变慢的是常驻约 1.6k–2.7k tokens、19–37 个生成文件，以及模糊请求自动完整化带来的额外阅读、询问、证据和审计步骤。

因此建议保留三项核心：**单一正典、最小路由、机器检查**；收缩默认档位、常驻内容和无条件生成物。这样能保留治理可信度，同时显著降低首次成功时间和日常小改动的仪式成本。
