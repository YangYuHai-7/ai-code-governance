1. 按 [试点协议](pilots/2026-09-10/试点协议.md) 建立 U01–U10 十个技术层级不同的模拟 persona；原始建设位于 `/tmp/aicg-pilot-20260910/`，最终候选原地升级复测位于 `/tmp/aicg-final-pilot-20260910/`。

3. 每个应用先运行失败测试，再完成最小实现；至少保留一个成功与两个失败/边界测试，并运行应用 smoke、`aicg check` 与 `aicg complete --verify`。

5. 本汇总只引用十份试点报告与其中记录的命令、源码行和探针现象，不把模拟评分或结构门禁外推为市场、客户或认证证据。

## 缺陷聚类

### P0

1. **核心用户故事没有从真实入口闭环。** U01 没有任何提醒触发；U07 对外 API 无法创建或推进 issue；U10 HTTP 无法加入成员。U05 的取消也只存在领域 API，按 P1 处理。共同问题是单元测试验证了内部类，却没有证明报告中的用户 surface 可达。
2. **认证或密钥配置 fail-open。** U06 使用公开默认 webhook secret；U07 信任可伪造的用户/租户请求头；U08 写接口无认证；U09 使用公开默认读写 token；U10 信任 body actorId。结构检查与 domain unit tests 都没有发现这些入口级绕过。
3. **关键数据一致性可被真实运行方式破坏。** U04 的文件快照整体覆盖在多实例下静默丢写并破坏 SKU 全局唯一性，是已复现的发布阻断缺陷。

### P1

1. **业务约束被“记录”，但没有形成 routed verification。** U01 的完成/提醒约束、U07 的 active membership、U08 的状态/金额、U10 的 workspace 权限均进入文档或配置，却没有一对一映射到 acceptance case；`complete ok=true` 因此容易被误读为业务完成。
2. **持久化、并发、失败恢复普遍缺失。** 十个应用都存在数据、幂等、事件、审计或恢复边界；U02/U03/U05 刷新丢数据，U06/U08/U10 的幂等/事件只在单进程成立，U09 没有可持续 key/data lifecycle。
3. **高风险场景没有专项威胁与负向证据。** Webhook、多租户、账单、凭据、workspace authorization 主要依赖操作者自行想出风险；complete 深度生成的 backend Skill 仍是通用 routing shell。
4. **原生浏览器与 native Node surface 长期落入 generic-unknown。** U01–U07 没有得到货币精度、浏览器持久化、a11y、请求预算、API 错误、文件一致性等表面能力提示。
5. **命令与 script 生命周期有可避免摩擦。** U08–U10 在正常增加 npm scripts 后 manifest stale，需要 sync；`npm test` 与 discovered `npm run test` 等价却被字符串级拒绝。
6. **novice 本地化和单步 CTA 不足。** U01/U02 选择 zh-CN 后，诊断仍以英文 JSON、Git/manifest/enforcement 等术语为主；U01 无法在不依赖 Builder 的情况下独立完成。

### P2

1. 多个 HTTP server 缺少 body 上限、稳定错误码、请求/关联 ID、安全响应头或准确启动日志。
2. U01/U03 等把 UI 或 HTML 压入服务文件，U09 暴露 debug 存储读取，U10 事件缺少 actor、id、版本与时间，维护和审计边界偏弱。
3. 前端试点普遍没有真实浏览器、窄屏和辅助技术自动化；后端试点缺少错误映射、故障注入与跨进程测试。

## 亮点

- 同一 tarball 的 project-local 安装和调用路径在 10 个隔离项目中均可复现，安装是评分最高维度。
- 所有 Builder 都保留了测试先红后绿，并满足至少一个成功与两个失败/边界测试的最低数量要求。
- module-first 目录建议普遍产生清晰的 `src/app -> src/modules/<domain>` 方向；U08/U09 的 repository/crypto 可注入，U10 的 shared EventBus 不依赖业务模块。
- AICG 没有把结构检查夸大为业务 enforcement：即使测试和 complete 通过，所有报告仍显示 enforced 与真实客户端验证为 unverified。
- simulated receipt 没有被升级为 real-project 或 certified，证据资格边界正确。

## 生产级判定与证据边界

**生产级通过率：0/10。** 该判定不是说十个 demo 都不可运行，而是没有任何一个同时具备完整用户入口、关键业务不变量、可信认证/权限、持久化与恢复、生产运行边界及相应负向证据。U02、U03、U05 虽无 P0，仍有明确 P1 阻断；其余七个存在 P0。

本轮不能支持以下说法：

- “10 位真实用户验证通过”；
- “已有真实客户采用”；
- “AICG 已在真实 Codex/Claude/Cursor 工作流中验证”；
- “generic/backend capability pack 已获生产认证”；
- “`check` 或 `complete ok=true` 代表业务、安全或生产就绪”。

本轮能够支持的结论仅是：候选包在受控 macOS 模拟环境中完成了十次可重复的 project-local 初始化和结构/项目命令验证；独立 reviewer 找到了可行动的产品与应用缺口；AICG 当前的 unverified/simulation-only 边界没有被错误升级。

后续产品取舍见 [功能决策](pilots/2026-09-10/功能决策.md)。
