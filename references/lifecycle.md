# L11 成长闭环：怎么让框架不腐烂

框架的默认命运有两种，都是死：
- **膨胀**成一堆没人读、AI 也加载不完的 Markdown。
- **被绕过**——门禁常关，ack 成为默认动作。

这一层是唯一对抗它的东西。**没有 L11 的框架，交付当天就是它最好的一天。**

---

## 闭环

```text
真实事件（AI 犯错 / 评审重复指出 / 事故 / 新人提问 / 门禁误判）
   │
   ├─► 记为候选（一行，进 candidates 清单，不立刻改框架）
   │
   ├─► 判定：够不够格进框架？（晋升判据）
   │      不够 → 留在候选，或直接丢弃
   │
   ├─► 判定：该进哪一层？（晋升目标）
   │
   ├─► 落地：改那一层的一个文件（不是新建一个文件）
   │
   ├─► 判定：这条能被机器检查吗？能 → 加进 L8，并让它失败一次
   │
   └─► 周期性健康检查 → 退休不再有效的部分
```

两个关键动作常被跳过：**"记为候选而不立刻改框架"** 和 **"退休"**。跳过前者会让框架被一次性事故塞满；跳过后者会让它只增不减。

---

## 候选来源

把这些明确写进 `docs/ai/lifecycle.md`，否则"框架该改什么"永远只靠某个人的记性：

| 来源 | 信号强度 | 怎么捕获 |
| --- | --- | --- |
| **AI 在本仓库犯过的错** | 最强 | 每次纠正 AI 之后问一句"这条本来该写在哪一层" |
| **代码评审反复指出同一件事** | 最强 | 第二次出现就记候选；第三次必须落地 |
| **生产事故 / 数据事故** | 强 | 事后复盘里必答"框架里哪一层本该挡住它" |
| **门禁误判（被 ack 的原因）** | 强 | 读 ack 理由；同一个理由出现 3 次 = 门禁判据错了，不是人错了 |
| **新同事 / 新助手问的问题** | 中 | 他们问的正是入口层没说清的 |
| **`gate_blocked` 记录** | 中 | 反复被同一个先存在问题挡住 = 有笔技术债该单独立项 |
| **上游工具能力变化** | 中 | 新客户端出现、旧客户端加了钩子 API → L0/L1/L10 要更新 |
| **文档里的陈旧措辞** | 弱 | 由 L8 的陈旧措辞检查产出 |

候选清单本身很轻：

```markdown
## Candidates
- [ ] 2026-08-14 AI 第二次在没有权限门的接口上加了写操作 → 候选：L3 权限规则 / L8 检查
- [ ] 2026-08-19 `drift_check` 被 ack 三次，理由都是"只改了注释" → 候选：收窄核心层目录判据
```

## 晋升目标：一个洞见该进哪一层

按这个顺序问，**取第一个成立的**：

| 问 | 是 → 放进 |
| --- | --- |
| 这是一条**必须永远成立**的禁令/要求，且能被判定？ | **L3 常驻规则**（`00_always.mdc`，谨慎——这层要小） |
| 这条只在**某类工作**里成立？ | **L3 档案规则** + 在 L2 的对应档案里引用 |
| 这是一个**已经犯过的具体错误**，需要展示对错？ | **L4 反模式**（Wrong / Right / Why wrong） |
| 这是一段**会重复执行的流程**？ | **L5 命令**（可带用户参数） |
| 这是一类**任务触发的专门知识**？ | **L5 技能**（`description` 决定它能不能被发现） |
| 这是**模块当前行为的事实**？ | **L6 知识层**，不是规则 |
| 这条能被**代码判定**？ | **L8 检查器**（同时也可以写进规则，但检查器才是强制力） |
| 这是**卡住时该怎么办**？ | **L9 fallback 策略表** |
| 这是**每次会话都要发生的动作**？ | **L10 钩子** |

判定不出来 → 它可能还不够具体，退回候选清单，等下一次发生把它说清楚。

**优先级次序**：能进 L8 就进 L8，不要只写成散文（P5）。能写成 L4 具体例子就不要写成 L3 抽象禁令——抽象禁令 AI 判定不了。

---

## 晋升判据（不是每个洞见都该进框架）

四条**全部**满足才落地：

1. **发生过 ≥ 2 次**，或单次后果不可忽略（数据损坏、安全、对外契约破坏）。
2. **后果具体**：能说出"不遵守会发生什么"。说不出来的规则就是偏好，不是规则。
3. **能写成可判定的指令**：读完能判断"我现在符合还是不符合"。"要写高质量代码"不合格。
4. **工具解决不了**：能靠 linter / formatter / 类型系统 / CI 自动挡住的，去加工具，不要加规则。规则是给工具管不住的部分留的。

第 4 条最常被忽略。**一条能被 linter 管住的事写成散文规则，是在用 AI 的注意力预算买一个免费的东西。**

---

## 退休判据

任意一条成立 → 删掉或合并（**删除是维护动作，不是损失**）：

- 它防的失败模式**已不可能发生**（技术栈变了、那段代码没了）。
- 它已被**更强的机器检查**取代（规则散文与检查器重复 = 两份需要维持为真的事实，P1）。
- 它**从未触发过**，且没人能说出它防的是什么。
- 它与另一条规则**重叠**：合成一条，保留更具体的那条表述。
- 它描述的是**一次性事故**的细节，而不是一类失败。

退休时要做的：删掉正文 → 检查有没有别处引用它（L8 的链接检查会告诉你）→ 如果它有配套检查器逻辑，一起删。

## 周期性健康检查

节奏：每季度，或每 N 个 PR，或每次有人说"框架挡不住事"时。清单：

**结构**
- [ ] `<pkg> run gate` 通过，且耗时仍在可接受范围（超过 ~5 秒会开始被跳过）。
- [ ] 每个客户端适配器仍指向正典路径（没有被替换成真文件）。
- [ ] 钩子探针跑通；跑不通的层在 README 里被标为「未验证」。

**内容**
- [ ] L3 常驻规则仍然全部是**必须永远成立**的（这层最容易膨胀）。
- [ ] 每个档案的 `required` 清单仍然是"读完这些就能开工"的最小集，不是"相关的都塞进来"。
- [ ] L4 每条反模式都还是真实发生过的，不是想象的。
- [ ] 知识层每个模块页的 `Verification Notes` 指向的文件还存在。

**强制力**
- [ ] 过去一个周期里检查器**真的失败过**（一直全绿：要么很好，要么它没在检查东西——去故意破坏一个文件验一次）。
- [ ] ack 频率与理由分布：某个门禁被高频 ack → 判据错了，修判据。
- [ ] `<PREFIX>_AI_GATE=off` / `_HOOKS=off` 是否已成为某些人的默认（问一句就知道）。
- [ ] warn 数量没有在长期上涨（warn 是"以后再说"的堆积处）。

**覆盖**
- [ ] 上个周期真实发生的 AI 错误里，有几条已经进了框架？零 = 闭环断了。
- [ ] 有没有层是"建了但没人用"的（尤其 L9）？没人用就降级或删掉，不要留着装样子。

## 值得盯的少量指标

不要建仪表盘，就这几个数，人工看：

| 指标 | 健康信号 | 危险信号 |
| --- | --- | --- |
| 门禁链耗时 | 稳定在秒级 | 缓慢上涨 → 会被跳过 |
| 门禁失败次数 | 偶尔失败 | 长期零失败（没在检查）或天天失败（判据太严） |
| ack 次数与理由 | 少、理由各不相同 | 多、理由重复 → 判据错 |
| 常驻规则行数 | 基本不变 | 单向增长 → 正在变成没人读的文档 |
| 标为「未验证」的层数 | 递减 | 递增 → 框架在长成装饰 |
| 闭环回写条数 | 每周期 ≥ 1 | 0 → L11 已死 |

---

## 框架自身的变更也要走同一套

改框架不是特权操作：

- 框架变更也要过 `<pkg> run gate`（检查器检查框架自身，这正是它最原始的用途）。
- 加一条能被机器检查的规则时，**同一次改动**里加检查，否则它永远不会被加。
- 新加的检查器逻辑要**故意破坏一次**证明它会失败（P5）。
- 改了正典目录的结构 → 同步入口层的阅读顺序与所有适配器（L8 的引用完整性检查会抓到漏的）。
- 框架变更也记在候选清单的"已落地"区，附上它对应的真实事件——**半年后判断该不该退休时，唯一有用的信息就是"它当初为什么被加进来"**。

## 元反模式（这一层最常见的死法）

| 反模式 | 后果 |
| --- | --- |
| 只增不减 | 框架变成 AI 加载不完的文档堆，于是它谁都不读 |
| 把一次性事故写成永久规则 | 规则里混入噪音，真规则的可信度被稀释 |
| 洞见落地成"新建一个文件" | 层数膨胀；同一个概念散在三处 |
| 加了规则但不加检查 | 一年后无人遵守，且无人知道（P5） |
| 健康检查从不做 | 腐烂只有在被绕过时才被发现，那时已经晚了 |
| 只有一个人懂这套框架 | 那个人离开，框架当天变成考古现场——所以每层都要写「它防的是什么」 |
