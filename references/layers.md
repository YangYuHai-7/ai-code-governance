# 十二层参考架构

逐层：**职责 / 文件形态 / 内容规格 / 不要写什么 / 验收**。

标注说明：
- **[标准]** = 已有事实上的行业约定（客户端会自动加载或社区普遍采用），照着做即可。
- **[发明]** = 本参考架构的设计，没有外部约定；命名可以改，**思想不要改**。

---

## L0 入口与引导 [标准]

**职责**：让任意客户端、任意会话从第零轮就拿到同一套规则，并知道接下来读什么。

**文件形态**：

| 文件 | 角色 |
| --- | --- |
| `AGENTS.md`（仓库根） | 正典入口：所有权阶梯、操作规则、加载顺序、验证命令表 |
| `CLAUDE.md`（仓库根） | **仅指针** + 常驻规则的 `@` 导入。显式声明"本文件不新增任何规则" |
| `.cursor/rules` → `docs/ai/rules` 等 | 适配器符号链接，按需要支持的客户端建 |

**内容规格**（`AGENTS.md`）：
1. 一句话说明本仓库/本目录拥有什么、不拥有什么（monorepo 与仓库族尤其重要）。
2. **加载顺序**（编号列表），并指向机器可读版本（`context-map.yaml`）。
3. 操作规则（编号，便于在对话里引用"规则 5"）。
4. 验证表：命令 → 覆盖什么 → **不覆盖什么**。
5. 完成门禁指针（不重述门禁内容）。

**不要写什么**：不要在 `CLAUDE.md` 里写独有规则——它会变成只有一个客户端遵守的影子规则源。`CLAUDE.md` 的唯一附加价值是 `@` 导入让常驻规则在第零轮就在上下文里，而不是等谁去跟随一个指针。

**验收**：决策账本必须先记录用户确认的 `all_built_in` 或 `selected`；A2 里选的每个客户端都能触达常驻规则，未选客户端不得被声称支持。这条要有检查（客户端选择—适配器平价性），不能靠检测结果或人记得。

## L1 常驻规则 [标准]

**职责**：唯一一个**每个任务都加载**的规则文件。它是预算最紧的文件。

**文件形态**：`docs/ai/rules/00_always.mdc`，front matter 声明 `alwaysApply: true`。

**内容规格**（≤80 行，四节）：

1. **Purpose** — 一句话 + 「先读本文件，再用 context map 选任务规则」。
2. **Non-Negotiables** — 5–10 条。典型通用条目：
   - 正典文档根在哪；适配器目录只能是适配器。
   - 代码与测试的权威性高于文档（P3）。
   - 保护用户改动：不 revert、不覆盖、不清理无关工作，除非用户明确要求。
   - 为可扩展性、可维护性、低耦合、下一个人的可读性优化。
   - 优先沿用邻近实现模式，再考虑新抽象。
   - **反过度设计**：不要加透传包装、重复注册表、兼容层、校验层，除非它消除了一处具体的现存重复或强制了一个已验证的共享不变量。
   - 改动范围限定在用户请求内。
3. **Loading Flow** — 5 步编号：读入口 → 选最小档案 → 加载 required → 按触碰面加载 optional → 改既有模块前加载它的知识页。
4. **Completion** — 行为变更后同步知识层；持久约定升级为规则/skill/策略；总结要写清改了什么、验证了什么、还有什么 gap。

**不要写什么**：任何只适用于某类任务的规则（那属于 L3，由档案触发）。常驻规则每多 10 行，所有任务都付费。

**验收**：front matter 可解析；文件里引用的每个路径都存在；行数在预算内。

## L2 上下文路由 [发明]

**职责**：把"用户说的话 + 改的文件"映射到"该读哪些文件 + 该跑哪些命令"。

**文件形态**：`docs/ai/context-map.yaml`。机器可读是刻意的：它同时被人、被助手、被检查器消费。

**内容规格**：

```yaml
version: 1

default_start:            # 任何任务都先读这三样
  - AGENTS.md
  - docs/ai/context-map.yaml
  - docs/ai/rules/00_always.mdc

verification_profiles:
  - docs/ai/verification-profiles.yaml

selection_order:          # 选档规则，散文，5–6 条
  - 用触发词与触碰路径把请求匹配到一个或多个档案。
  - 实现前加载该档案的 required 文件。
  - 只在触碰的行为需要时加载 optional 文件。
  - 改既有模块前加载它的知识页。
  - 选最终检查前加载验证档案。
  - 代码/测试与文档冲突时优先信代码。

profiles:
  <profile-name>:
    description: 一句话，说明什么样的改动属于这个档案
    triggers:
      en: [关键词...]
      zh: [中文关键词...]
      paths: [触发的目录或文件...]
    required: [实现前必须读的文件...]
    optional: [触碰到才读的文件...]
    verify: [该档案的验证动作，可以是命令也可以是散文动作...]

completion:               # 所有实现类任务共同的收尾
  implementation_tasks:
    required: [收尾时才加载的规则，例如留痕与知识同步规则]
    actions: [跑最强本地验证 / 同步知识层 / 显式记录 gap / ...]
```

**档案怎么切**：按**工作种类**切，不按代码目录切。3–6 个起步。常见的通用集合：

| 档案 | 覆盖 |
| --- | --- |
| `<主要实现类>` | 本仓库最高频的实现工作（加接口 / 加页面 / 改组件） |
| `data-migration` | 数据修复、回填、导入导出、一次性脚本 |
| `api-docs` / `contract` | 契约对齐、注释与实现一致性、跨端交接说明 |
| `review` | 评审、合并就绪、风险审计、只验证不改代码 |
| `planning` | 多步计划、需求分析、跨会话任务 |
| `git-workflow` | 分支、提交、MR、rebase、冲突 |
| `framework`（自托管） | 本治理框架自身的改动 |

**不要写什么**：
- 不要凭空发明档案。用户答不出 D2 时只建一个 `default`，注明档案随模式浮现而增加。
- 不要让 `required` 无限膨胀。判据：这个文件对**该档案的每一个**任务都必要吗？否则它是 `optional`。
- 触发词不要只写英文（母语非英语的团队会选不中档案）。
- 不要用能跨所有权边界的宽词代替领域术语。例如同仓库同时存在“产品 AI 风险治理”和“AI 编码
  治理”时，单独的 `AI 治理` 必须由前缀、排除词或可执行样例消歧。
- 路径可以有意多档命中，但必须声明预期的有序 profile set；UI 的宽路径不得无意覆盖 API 子树。

**验收**：检查器验证 `required` / `optional` / `verify` 里引用的**每个路径都存在**；声明为必需的
glob 必须至少命中一个对象；profile registry 不能为 null/空且至少包含仓库证据要求的档案。另维护一组
真实请求/路径 → expected ordered profiles 的 routing examples，覆盖单档、显式多档、相似领域名与父子路径；
碰撞或漏选时探针失败。只验证文件引用不算验证路由语义。

## L3 领域规则与策略 [标准形态 / 发明编号法]

**职责**：具体的、可执行的实现约束。**由档案触发，不常驻。**

**文件形态**：`docs/ai/rules/NN_<关注点>.mdc`，front matter：

```yaml
---
alwaysApply: false
profiles: [哪些档案会加载它]
---
```

编号按关注点分段留出插入空间，例如：

| 段 | 关注点 |
| --- | --- |
| `00_` | 核心约定（文档加载、代码风格门禁、注释语言、常量） |
| `05_` | 工作流（实现前的必需步骤、任务分级、评审完成契约） |
| `10_` | 架构分层与职责边界 |
| `12_` | 契约与校验 |
| `15_` | 命名与路径 |
| `20_` | 错误、国际化、安全 |
| `22_` | 可扩展性（注册表、扩展点、私有成员） |
| `30_` | 常量与配置 |
| `40_` | 性能（批量、分页、避免 N+1） |
| `45_` | 会话留痕与知识同步（收尾时加载） |

**`policies/` 子目录**：比规则更窄、更像判定表的东西（某类字段的表示约定、敏感数据处理）。规则说"怎么做"，策略说"这一类东西的唯一正确形式是什么"。

**内容规格**：每条规则要能被指着说"违反了"。可以引用具体文件路径、具体 API、具体命令。**不要写"应该保持良好的可读性"这类无法判定的句子。**

**不要写什么**：不要一次生成 14 条。规则数量应该等于用户在 D1 里能举出实例的数量。宁可 4 条真规则，不要 14 条通用规则——后者教会读者"这份文档是虚构的"（元反模式第一条）。

**验收**：front matter 可解析；`profiles` 里的档案名在 context map 里存在；每条规则能追溯到 D1 的一个回答。

## L4 反模式 [发明]

**职责**：记录本仓库**历史上真实出现过**的错误写法，以及为什么不能再写。

**文件形态**：`docs/ai/anti-patterns.md`，每条固定结构：

```markdown
## N. 短标题

**Wrong**
<反例代码>

**Right**
<正例代码>

**Why wrong**
- <后果>
- <关联的规则 / skill 链接>
- <判定方法：怎么区分"历史包袱"与"本次新增">

**Exception**: <什么情况下反例形态是对的>
```

**为什么单独成层**：规则说"要怎么做"，反模式说"这个看起来合理的写法为什么错"。后者不能用前者表达——它需要并列两段代码。而且它是 review 结论最自然的沉淀位置（L11 的提升目标之一）。

**不要写什么**：不要放没在本仓库发生过的假想错误。不要省略 Why（P7）。不要省略例外条款——没有例外条款的禁令在真实例外出现时会被整条丢弃。

**维护规则要写在文件里**：发现新反例当场编辑，不要攒着"以后整理"。

## L5 能力层：skills / commands / agents [标准]

三种形态，边界要划清，否则会互相重述。

### skills — 任务触发的怎么做

**文件形态**：`docs/ai/skills/<name>/SKILL.md`，front matter 必须有 `name` 与 `description`。

**`description` 是唯一的选中机制**：它必须包含触发条件与触发词（含母语）。缺 `description` 的 skill 不是报错，而是**静默不可发现**——这正是它必须被机器检查的原因。

**内容规格**：必读的规则清单 → 放置位置表 → 骨架 / 步骤 → 常用导入或工具 → 执行清单（checklist）。

**skills 与 rules 的边界**：规则是"必须成立的约束"，skill 是"做这类任务的操作指南 + 例子"。skill 引用规则，**不重述规则正文**。

### commands — 可重复流程

**文件形态**：`docs/ai/commands/<verb>.md`，front matter 一个 `description`。

**内容规格**：编号步骤，每步指向要加载的档案/skill 或要跑的命令。加一节「可选用户后缀」：用户可能在命令后追加自由文本（"contract 模块，GET 详情"），说明怎么解析它，以及**只在仍然含糊时问一个**澄清问题。

### agents — 分阶段角色

**文件形态**：`docs/ai/agents/<role>.md`。

一套通用的分阶段角色（按顺序）：

| 角色 | 职责 | 关键约束 |
| --- | --- | --- |
| `requirements-clarifier` | 把碎片需求变成结构化验收标准 + 开放问题 | 不设计实现 |
| `codebase-explorer` | 只读现状地图：相关代码、约定、测试 | 不改文件、不提方案 |
| `<domain>-architect` | 实施方案：契约、分层、数据、权限、错误 | 不写完整代码 |
| `risk-auditor` | **独立**风险审查，按清单挑刺 | 不和架构师妥协；不给"看起来不错"式评审；找不到风险也要说"按 X 清单核查后无重大风险，残留风险：…" |
| `implementation-planner` | 把方案拆成小而有序的任务 + 每步验证 | 不重新设计范围 |
| `implementer` | 逐任务执行已批准的计划 | 不重新设计范围 |

`risk-auditor` 的输出格式值得固定（Critical / Important / Minor + 每条写"现象 / 风险 / 修复方向"+ 验证假设 + 残留风险），因为它的价值全在于**可被逐条决策**。

**不要写什么**：不要为每个角色再造一套规则；角色文件里列"必读"清单，指回 L1/L3/L6。

**验收**：除了 front matter 和 inventory 完整性，还要验证每个 skill、command、agent 至少有一条可达路径：默认入口直接指向、context map 档案/能力目录指向，或声明客户端的原生适配器已验证加载。`USAGE.md` 可以作为能力目录，但 context map 或入口必须先能触达它，且目录内必须链接到实际文件。只有名称和描述而没有加载路径，状态只能是 `present`。

## L6 知识记忆层 [发明]

详见 [memory-layer.md](memory-layer.md)。摘要：

- `docs/memory/<module>/README.md` = 该模块的**当前状态**（P11），必需章节固定。
- `docs/memory/<module>/<细分>/<topic>.md` = 某个流程逻辑非显然时的专页。
- `docs/memory/sources/` = 影响了知识层的需求、会议、审计、评审原文，front matter 声明**来源类型 + 敏感级别 + 验证自哪些代码文件**。
- `INDEX.md` = 页面 → 数据路径的索引，且**每个生成物都要有 owner**。
- 页面内嵌 `memory-check` 断言块，让"这个接口/方法仍然存在"可被机器验证。

---

## L7 验证档案 [发明]

**职责**：把"我改了这一片，该跑什么"变成查表，而不是每次重新发现。

**文件形态**：`docs/ai/verification-profiles.yaml`。与 L2 的区别：L2 回答**读什么**，L7 回答**跑什么**。刻意分开，因为它们的变更节奏不同（L7 跟着工具链走）。

**内容规格**：

```yaml
version: 1
profiles:
  <name>:
    description: 一句话
    paths: [触发这个档案的路径...]
    memory: [该档案对应的知识页...]      # 可选
    commands:                            # 有序，从便宜到贵
      - <语法检查 触碰文件>
      - <lint 触碰文件>
      - <定向测试>
      - git diff --check
    fallback:                            # 已知的环境坑与替代路径
      - 如果 <已知问题>，改用 <替代命令> 并记录 gap
    notes:
      - 该档案特有的注意事项
```

**关键设计点**：
- **命令刻意收窄**（只跑触碰文件），只在改动触及共享行为时放宽。
- `fallback` 记录**已知的环境坑**（某个运行时版本下测试框架跑不起来之类）。没有这一节，每个人都会重新踩一遍并各自发明一个绕法。
- 框架自身要有一个档案（自托管），否则改治理层的人不知道该跑什么。
- `AGENTS.md` 只指向本文件并解释覆盖边界，不复制“改动类型 → 命令组合”。同一 DoD 在入口、context
  map 与 verification profiles 三处各写一份，会产生三个合法答案。

**验收**：检查器验证 `profiles` 是非空 object、每个 profile 有 description/paths/commands，`paths` 与
`memory` 里的引用存在，required glob 至少命中一个对象，命令对应真实入口。故意把 profiles 设为 null/
空、换成零匹配 glob 或删除自托管 profile 时必须失败。

详见 [gates-and-hooks.md](gates-and-hooks.md)。它把 L1–L9 的建议性部分变成运行时事实。注意：目前只有部分客户端有生命周期钩子 API，所以这一层**必然**是不均匀的——README 里要老实写清哪个客户端被绑住了、哪个没有（P5）。

详见 [lifecycle.md](lifecycle.md)。回答唯一真正决定框架寿命的问题：**一次失败怎么变成一条规则，一条规则什么时候该死。**

## 层间依赖

```text
L0 入口 ──┬─> L1 常驻规则
          └─> L2 上下文路由 ──┬─> L3 规则/策略
                              ├─> L5 能力层（skills/commands/agents）
                              ├─> L6 知识层
                              └─> L7 验证档案
L8 检查器 ──> 校验 L0/L1/L2/L3/L5/L6/L7 的引用完整性与自身平价性
L9 运行时 ──> 消费 L2 分类 + L7 命令，产出 task 状态
L10 钩子  ──> 注入 L0 阅读顺序；在结束时执行 L8
L11 闭环  ──> 把真实失败回灌 L3/L4/L6/L8
```

读法：**L8 指向所有内容层**（它是防腐层），**L11 从所有层回流**（它是进化层）。缺 L8，内容层腐烂；缺 L11，框架冻结在建立那天的认知上。
