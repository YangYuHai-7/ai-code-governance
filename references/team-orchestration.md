# 专家团队与角色编排

治理产品需要互相制衡的能力，不是一个“全能提示词”。一个人可以兼任多个角色，但侦察、方案和独立审计不能在同一个思考步骤里混为一体。

## 核心角色

| 角色 | 需要的人才 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 治理架构师 | 软件架构、平台治理、跨仓所有权 | 治理拓扑、正典、层次、版本边界 | 发明业务规则 |
| 代码考古与领域分析师 | 代码阅读、Git 历史、领域建模 | 真实结构、事故、反模式和术语证据 | 决定目标架构 |
| 访谈与知识工程师 | 需求澄清、知识建模、技术写作、本地化 | 多轮访谈、决策账本、记忆 schema、中英一致性 | 替用户做业务决策 |
| 技术栈专家 | 对应前端、后端、移动或系统平台经验 | 能力包、边界、命令发现、适配风险 | 把通用最佳实践强塞进项目 |
| 治理工具工程师 | 构建系统、静态分析、Git hooks、跨平台脚本 | 检查器、门禁、钩子、安装、升级和三系统兼容 | 用散文代替可执行检查 |
| 对抗评测工程师 | 测试策略、安全思维、故障注入 | 负向探针、组合矩阵、残留风险、误判分析 | 为赶发布降低证据等级 |

按风险召集安全、隐私、法务、无障碍、DevOps 或行业合规专家。他们是条件角色，不应被一个通用“安全专家”标签替代。

## 用户的角色

用户或项目负责人是治理产品 Owner，拥有以下不可委托决策：

- 项目硬边界和业务风险容忍度；
- 允许哪些门禁阻止提交或结束会话；
- 技术栈和 UI 方案最终选择；
- macOS、Windows、Linux 的正式支持范围；
- 哪些信息可以进入知识层；
- 何时接受 `unverified` 能力包继续推进。

模型可以推荐，不能静默替用户批准。

## Agent 映射

按阶段建立上下文隔离角色：

| 阶段 | Agent | 输出 |
| --- | --- | --- |
| 1 | `governance-repository-explorer` | 只读事实、路径、命令、冲突与置信度 |
| 2 | `governance-requirements-facilitator` | 验收标准、决策账本、开放问题 |
| 3 | `governance-architect` | 拓扑、层次、文件计划、强制边界 |
| 4 | `<stack>-specialist` | 能力包适配报告，不直接修改目标代码 |
| 5 | `governance-implementer` | 只执行已批准阶段 |
| 6 | `governance-adversarial-auditor` | 分级发现、负向探针、平台矩阵和残留风险 |

探索 Agent 不出方案；架构 Agent 不宣布通过；实现 Agent 不改变范围；审计 Agent 不替实现者修饰结论。

## 交付顺序

1. 治理架构师确定目标仓库的所有权和拓扑。
2. 代码考古角色收集事实；技术栈专家只补充无法从仓库确定的解释。
3. 访谈角色与用户建立并确认决策账本。
4. 架构师给出分阶段文件计划、门禁链和证据边界。
5. 工具工程师与实现角色逐阶段落地，每阶段跑最小验证。
6. 对抗评测角色独立执行负向探针与 macOS/Windows/Linux 组合审查。
7. 用户验收一次真实任务；知识工程师记录当前状态和 known gaps。

完整模式在第 6 步完成前不得宣布“框架已完成”。审计角色要从声明—证据矩阵反向抽样：至少选择
一个结构声明、一个语义声明和一个运行时声明，独立复现其负向失败；L9/L10 存在时还必须独立跑一次
正常成功闭环，防止“只会阻断、不会恢复”。若环境没有独立 agent，必须在实现步骤结束后以新的审计
上下文执行同一清单，并把“非独立角色”列为证据边界。

## 团队内部 B 的运行方式

- 每个能力包指定一名栈 Owner 和一名独立评测 Owner。
- 新发现先进入候选清单，重复出现或高风险才晋升为规则。
- 每次使用记录能力包版本、项目模式、OS、结果、误判和人工干预。
- 每月审查门禁耗时、逃生舱理由、未验证项和规则退休候选。

## 演进为产品 C

产品化新增的是发布责任：

- 机器可读的能力包清单与兼容范围；
- 稳定的安装、升级、回滚和弃用协议；
- 匿名化的认证证据，不携带客户代码或内部业务规则；
- 每个客户端和操作系统的加载、适配器与钩子状态；
- 清楚区分内核缺陷、能力包缺陷和目标项目特有问题；
- 发布说明只承诺实际跑过的组合。

不要把内部项目名称、目录、API、事故细节或品牌规则带入可分发包。可迁移的是方法、schema、测试协议和已经去项目化的能力包证据。

## 机器可读的团队建议边界

`aicg team` 使用 `assets/team-role-registry.json` 为项目输出确定式的**人类职责覆盖建议**。它只读取精确依赖与用户确认的业务上下文；业务描述本身不进行关键词推断，也不写入、缓存或回显。每个建议必须分别列出 `stackEvidence`、`businessEvidence`、`confidence`、`assumptions` 和 `activationTrigger`，并明确可兼任关系与不能由同一实现者自我验收的责任分离。

该命令及聊天请求“给我团队建议”永远是只读：不得创建人员、Agent、任务、权限、文件、外部消息或招聘记录。它不输出人数、预算、工期或成功保证；技术依赖只说明声明的技术，不能证明生产使用、安全、合规或人员能力。输入必须是仓库内的普通 JSON 文件，不能经过符号链接；缺少明确 `teamScope` 或业务描述时返回 `needs-user-input`。

## AICG 产品团队成员池

`assets/aicg-product-team.json` 是 AICG 产品团队的版本化正典，记录 Product Owner、治理架构、CLI、Agent 集成、知识工程、独立评测、DevEx、安全、产品设计、控制平面、SRE、企业合规、DevRel、Sales/Customer Success 和技术栈认证专家池。每个成员都必须记录：

- 明确职责和不负责的边界；
- 能力标识、阶段和按需激活方式；
- 必须共同参与的角色；
- 必须保持独立的设计、实现和验收关系。

“加入团队”只表示进入 `approved-available` 成员池，不表示参与每个需求。没有明确需求能力时，`activeRoles` 必须为空；有需求时，只激活覆盖该需求的最小角色集合和不可省略的独立评测或决策角色。未激活成员不得读取额外上下文、扩大范围或输出意见。

## 动态增减角色协议

自然语言层先把当前需求转换成明确的 `requiredCapabilities`，再调用确定式分配器。若现有成员池不能覆盖某项能力：

1. 输出一个职责有界的 `proposedAdditionalRoles` 建议，写清职责、不负责事项、能力和独立性要求；
2. 返回 `needs-role-approval`，在对话中询问 Product Owner 是否同意添加；
3. 未收到明确同意前，不得把建议角色写入团队配置、加入成员池或激活；
4. 同意后，把相同定义记录为 `approvedAdditionalRoles`，并附 `approval.status=approved`、`approvedBy=product-owner` 和可追溯的 `evidence`；
5. 已批准扩展角色也仍然按需激活，需求结束后回到可用但未激活状态；长期不再需要时应通过新的 Owner 决策退休，不静默删除。

审批记录属于项目内的决策输入，而不是模型自己生成的授权。`aicg team` 只读取并验证该记录：审批证据不会回显，建议角色不会自动持久化。对话 Agent 在用户明确批准后才可通过独立的、有范围的文件变更记录它，并必须展示验证结果。实现者不能批准自己的角色提案，独立评测角色也不能替 Product Owner 作成员决策。

最小上下文示例：

```json
{
  "teamScope": "human",
  "businessDescription": "A local AI code-governance product.",
  "confirmedSignals": [],
  "requiredCapabilities": [
    "chat-intent-routing"
  ]
}
```

这一请求只会激活 Agent Integration Engineer 与其强制独立评测角色；其他已加入成员保持未激活。新增角色的定义和审批都保存在同一个仓库内普通 JSON 上下文中，因此可以评审、回滚和审计，而不会让只读建议命令暗中改变团队。
