# 核心思想：十二条

每条给出**主张**、**为什么**、**怎么落地**、**违背时的症状**。这些是跨技术栈通用的部分；具体规则内容永远来自目标仓库。

---

## P1 单一正典源 + 适配器

**主张**：规则、skills、commands、agents 只有一个正典目录（推荐 `docs/ai/`）。`.claude/`、`.cursor/`、`.codex/`、`.agents/` 只包含指回正典的符号链接，永不包含内容。

**为什么**：团队会同时用 3–4 个 AI 客户端，每个都有自己的自动加载路径。如果每个客户端一份拷贝，那么 N 个客户端 × M 个文件 = N×M 个需要同步的事实。第一次有人只改其中一份，规则就分叉了——而且分叉是**静默**的：每个客户端都自认为读到了权威版本。

**怎么落地**：
- 正典目录写内容；客户端目录只 `ln -s`。
- 检查器验证每个适配器符号链接**指向正确的正典路径**（不只是存在）。
- 有客户端不支持符号链接式规则目录（例如 Claude Code 没有 `.claude/rules` 约定）时，用它支持的机制（`CLAUDE.md` 的 `@` 导入）达到同一效果，并**单独检查这条平价性**——否则那个客户端会比别的客户端少拿到上下文，而没人发现。
- 在正典 README 里写一句「不要编辑适配器目录里的文件，不要在那里新建文件」。

**症状**：两个人对同一条规则的理解不同，各自都能贴出"文档写的"。

## P2 按档案路由上下文，而不是全量加载

**主张**：入口只加载三样：入口文件、常驻规则、上下文映射。其余按**任务档案**（profile）加载：一个档案 = 触发词（含团队母语）+ 触发路径 + `required` 文件 + `optional` 文件 + `verify` 命令。

**为什么**：上下文预算是有限且昂贵的。全量加载 docs 树的框架有两种死法：要么真被加载、把预算烧在与本任务无关的规则上，要么被助手悄悄忽略。**"最小可用上下文"不是省钱，是让被加载的每一份都真的被遵守。**

**怎么落地**：
- `required` 是「实现前必须读」；`optional` 是「触碰到那部分行为才读」。这个区分要写在文件里，不然全都会变成 required。
- 触发词分语言列出（`en:` / `zh:`），因为同一个任务在中英文里的说法完全不同，而模型的选档靠的就是词面匹配。
- 触发路径与触发词并列：用户说得含糊，但他们改的文件不含糊。
- 加一条 `selection_order`（选档顺序）说明：多档匹配怎么办、档案不确定怎么办、文档和代码冲突怎么办。
- 每个档案自带 `verify`，让"改完怎么验"不必每次重新发现。

**症状**：助手在做一个两行的改动时读了 40 个文件；或者反过来，从不读任何规则文件。

## P3 代码是事实来源，文档是快照

**主张**：仓库代码与测试的权威性高于任何文档。二者冲突时，在仓库里消除这个冲突，**不要发明第三条规则**。

**为什么**：文档由人维护，跑慢一拍是常态而非异常。把陈旧文档当设计参考，会复制错误的路径前缀、错误的字段名、已被删掉的抽象。这是 AI 助手最高频的一类错误，因为文档正好是它最容易读到的东西。

**怎么落地**：
- 写进常驻规则（L1），措辞要强："Repository code and tests outrank documentation."
- 文档的用途重新定义为「与实现比对是否漂移」，不是「设计参考」。
- 兜底策略里写明：docs 与 code 冲突 → 信代码 → 在同一次改动里更新文档。
- 反模式里放一条具体案例（"我看路由注释写的是 X 所以代码也写 X"）。
- 知识层（L6）里的具体断言要能被机器对着代码验证（见 [memory-layer.md](memory-layer.md)）。

**症状**：新代码复制了一个半年前就改掉的路径前缀，且 review 时看起来「和文档一致」。

## P4 完成由门禁判定，不由助手宣布

**主张**："done" 不是助手的措辞选择，而是一个状态：所有必需门禁通过，或被显式记录为受既有问题阻塞。

**为什么**：助手有强烈的收尾倾向——它会在还有未跑的检查时给出漂亮的总结。人类 reviewer 无法从总结里看出哪个检查没跑，因为**没跑的检查不留痕迹**。

**怎么落地**：
- 门禁清单按任务类型定义（见 [harness.md](harness.md)），不是一份通用清单。
- 门禁证据绑定一次具体的 implementation generation 或 change fingerprint。任务重新进入 `implementing` 后，旧的 passed/acked 立即失效；“旧证据证明新实现”必须由负向探针拦住。
- `complete` 只有一个受检入口。通用状态转移不能进入终态；完成入口必须原子校验 required gate 集合、证据、时间与 generation，不能只看当前数组里有没有 pending。
- 允许跳过 `optional` 检查，但必须留下明确的 gap 说明。
- 门禁被既有问题阻塞时用固定格式，不许含糊：

  ```text
  Gate: <name>
  Status: blocked by pre-existing issue
  Evidence: <命令 / 输出摘要>
  Next action: <具体清理动作或需要谁决策>
  ```
- 总结的固定三段式：**改了什么 / 验证了什么 / 还有什么是 gap**。第三段不许省略，"无 gap" 也要显式写。
- 报告验证结果时**按仓库/包分别报告**，并说明哪一侧你没有验证——一个包的门禁通过，对另一个包不构成任何证据。

**症状**：一段自信的完成总结，随后 CI 在第一条 lint 上就红了。

## P5 只有被检查的规则活着；其余必须标注

**主张**：每条治理声明要落进三类之一——**已强制**（存在会失败的检查）、**仅陈述**（只有散文）、**未验证**（没人证明客户端真的读了它）。交付时逐层给出这份台账。

**为什么**：仅建议性的框架有一个致命性质：**违反它不产生任何后果**。从未加载入口文档的助手也从未学到阅读顺序、门禁、记忆义务——而且什么都不会失败。于是框架的实际强制力等于零，但它长得像有强制力，这比没有框架更坏——它给了虚假的安全感。

**怎么落地**：
- 建 L8 检查器的优先级高于扩充 L3/L5 的内容量。
- 能被机器检查的东西比想象的多：文件存在性、YAML 里引用的路径存在性、符号链接目标正确性、front matter 完整性（缺 `description` 的 skill 是**静默不可发现**，不是报错）、markdown 本地链接可解析、反引号里的仓库路径存在、钩子配置存在、客户端引导平价性、陈旧措辞（例如已废弃的目录名仍出现在文档里）。
- 不能被机器检查的东西（改动范围是否恰当、review 是否充分）**明确标为助手责任**，写在检查器的注释里，避免误以为已被覆盖。
- README 里那段台账要带日期。

**症状**：框架文件齐全、检查器不存在；或有检查器但只检查它自己。

## P6 门禁与风险成比例，且批量在末尾跑

**主张**：门禁要求的强度取决于**这次会话改了什么**，不是取决于任务名。并且所有检查批量在任务末尾跑一次，绝不逐文件跑。

**为什么**：两个相反的失败。太松：文档级改动被要求完整仪式，助手学会把门禁当噪音、开始寻找绕过方式。太紧或太频繁：逐文件 lint 让一次 12 文件的改动跑 12 次门禁，慢到必然被关掉。

**怎么落地**：一张比例表，行是「改了什么」，列是各项要求。例如：

| 会话改了什么 | 门禁链 | 知识层同步 | 会话留痕 |
| --- | --- | --- | --- |
| 什么都没改，或只改文档 | – | – | – |
| 非核心代码（配置、工具链、测试） | 必需 | – | – |
| 核心层（业务/接口/数据层目录） | 必需 | 必需 | 必需 |

- 「核心层」的定义要落成一个**具体目录列表**，因为那正是行为与接口语义所在，也正是知识层所记录的东西。
- 行的选择依赖于正确解析改动集合——所以一个**漏报的改动清单是绕过，不是四舍五入**（"什么都没改"会跳过每一列）。见 [gates-and-hooks.md](gates-and-hooks.md) 的账本交叉核对。
- 允许「刻意更严的后备」：机器无法判断"这次核心改动是否真的很小"，所以宁可偶尔过度触发，配 P8 的审计式 ack。

**症状**：有人在 `settings.json` 里把钩子注释掉了，且提交信息只写 "chore"。

## P7 每条禁令必须可追溯

**主张**：`anti-patterns.md` 里每条禁令都有 **Wrong 代码 / Right 代码 / Why wrong**，且 Why 里链接到具体规则或引用一次真实的 review 结论、事故。

**为什么**：没有理由的禁令会被下一个撞上它的人删掉——他有一个看起来正当的用例，而文档没有任何东西能反驳他。有理由的禁令能被**正确地**删掉：当理由不再成立时。

**怎么落地**：
- 固定结构（标题 / Wrong / Right / Why wrong），并在文件末尾写「怎么维护此文件」：发现新反例**当场编辑**，不要攒着"以后整理"。
- 每条尽量给出**判定方法**，而不只是原则。例：「这是个历史包袱签名还是本次新增？用 `git log --diff-filter=A --follow <file>` 判断——早于本任务存在则保持签名不变，本次新增则用新写法。」
- 允许并显式写出**例外**。没有例外条款的禁令，在真实例外出现时会被整条丢弃。

**症状**：有人在 PR 里争论一条规则该不该存在，而没人能说出它当初为什么被写下。

## P8 逃生舱必须存在且被审计

**主张**：任何硬门禁都要配一个**带理由、限时、单次**的确认命令，以及一个环境变量级 kill switch。两者都留痕。

**为什么**：门禁必然误报——机器判断不了"这次核心改动确实微小"。没有逃生舱时，人会去关掉整个钩子（P6 的症状），那是不可逆且无记录的。有审计逃生舱时，绕过变成一条带理由的记录。

**怎么落地**：
- `<pkg> run gate:ack -- "<reason>"`：写一个带时间戳、理由、拥有它的 enforcement entrypoint 与 change fingerprint 的临时记录，**原子单次消费**（第一次读取即清除），并设一个短过期（例如 15 分钟）。
- 一个 kill switch 关单项门禁、一个关全部钩子，都在文档的「逃生舱」表格里列出。
- 门禁在 CLI、Stop 与 git hook 多处被消费时，**判定逻辑只写一份**（共享库里的一个函数），否则它们会静默地不一致。每个硬入口必须拥有并消费自己 scope 的 ack；不得让“CLI 只读不清”的共享文件在没有后续 consumer 时被重复放行。
- ack 用掉时，让门禁**打印它被 ack 了**以及理由，而不是静默通过。

**症状**：`git log` 里出现「临时关闭 hook」的提交，之后再没被打开。

## P9 后台守卫可降级，交付证据必须失败

**主张**：后台注入型 hook 自身出错时可以警告并 `exit 0`，避免客户端或仓库不可工作；但显式作为完成、pre-commit 或 CI 证据的 checker 自身异常、受管 schema 错误或必需输入不可读时必须非零。二者不能共用一句“fail open”。

**为什么**：ambient hook 崩溃不应让每次会话都停摆；显式 gate 若在跳过一整项检查后仍返回成功，则“通过”本身是假的。可用性和证据真实性分别由不同入口负责。

**怎么落地**：
- ambient handler catch 异常 → 打印哪个能力失效、要求人工确认什么 → `exit 0` → 把对应声明降级为 `unverified`。
- delivery checker catch 异常 → 收集成 failure、打印修复动作 → 非零退出。合法 JSON 但 shape 错、必需文件变成目录、解析器内部异常都属于失败，不是 warning。
- 只有依赖未跟踪本地产物、gitignored 目录、兄弟仓库或明确可选工具的条件可以 warn；warning 必须命名被跳过的断言，且该声明不能标 `enforced`。
- 版本控制无法解析时可 warning，但必须报告 change-set enforcement 未验证；在真实 checkout 中另跑条件探针后才能晋升。

**症状**：显式 gate 打印“checker crashed / 0 failures”并退出 0；或新同事只因一个本地可选链接不存在而完全无法工作。

## P10 任务状态外化

**主张**：中等以上、敏感、或预期跨会话的任务，把分类、权限、上下文清单、门禁、当前状态、兜底记录写进一个文件（`task.yaml`），而不是留在对话里。

**为什么**：上下文窗口会被压缩，会话会结束，用户会换工具。**留在对话里的状态等于没有状态。** 下一个助手（或压缩后的同一个助手）看不到原始讨论，会把"漂移"当成"现状"继续做下去——这是跨会话最危险的失败模式。

**怎么落地**：见 [harness.md](harness.md)。关键点：
- 一个状态机，禁止从模糊请求直接跳到 "completed"；禁止从失败态进入 completed。
- 用户改变范围 → 回到 `intake` 重新分类，而不是在原分类下继续。
- 上下文被压缩 → 从状态文件 + 最新留痕摘要恢复，**再采取新动作**。
- 状态目录 gitignore（它是本机可恢复性工具，不是团队产物），但模板与运行时文档进 git。

**症状**：第二次会话实现的是 A 方案，而第一次会话商定的是 B，且没人发现。

## P11 知识层写「现在是什么」，不写变更日志

**主张**：知识/记忆页面描述**当前代码状态**。不写实现如何演进、不写内部计划的决策编号、不写作者感想、不写 "TODO 未来工作"。

**为什么**：git log 已经记录了历史。知识层的唯一价值是「下一个会话打开这个模块时能直接信任的当前事实」。一旦它开始记录历史，它就同时变长和变假——而**变假的知识层比没有知识层更坏**：每个未来会话都从错误的前提开始。

**怎么落地**：
- 规定必需章节（模块概要 / 能力地图 / 接口面 / 核心业务逻辑 / 数据来源 / 相关模块 / 归属代码路径 / 验证说明）。
- 明确「不要写什么」清单。
- 强制**逐项一致性核对**：memory 里描述的每个行为在当前代码里仍存在（grep 函数名、路由、错误码、常量）；字段名对着实现的返回块核对（不是对着注释）；错误码对着抛错语句核对；索引对着 schema 声明核对。
- 把不确定留可见：`Known gap` / `Needs verification`，而不是删掉或含糊化。
- 让部分断言**可被机器验证**（见 [memory-layer.md](memory-layer.md)）。

**症状**：某页 memory 描述了一个三个月前就被删掉的接口，而新会话照着它写了调用方。

## P12 诚实的最轻仪式

**主张**：用「与风险相称的最轻流程」。小的只读回答和琐碎文档编辑不需要完整仪式；但**行为变更必须有定向验证与对应的文档同步**，不许用"任务小"来跳过。

**为什么**：一刀切的重仪式框架会被整体绕过（P6）；一刀切的轻框架在行为变更上失守。需要的是**分级的完成定义**，且分级标准写下来，而不是每次由助手临场判断。

**怎么落地**：
- 任务分级（小 / 中 / 大 / 敏感），每级给出：是否需要计划、是否需要留痕、是否需要知识层同步、验证强度。
- 一个任务同时符合多级时：**取更严的隐私/留痕规则 + 取最轻但仍保证可恢复与可审计的流程**。
- 分级表要给例子（"只读回答"、"错别字"、"跨模块特性"、"生产数据"），否则每个人的"中等"都不一样。
- 明确写下：分级不得用于跳过行为变更的验证。

**症状**：一次"小改动"改了权限判断，没有测试、没有文档同步，因为它"只有三行"。

## 正典所有权：一个事实只放一处

上面十二条之外，还有一条贯穿性的排布原则：**每一类知识有且只有一个正确位置。**

| 内容类型 | 归属 |
| --- | --- |
| 持久的实现约束 | `docs/ai/rules/` |
| 任务特定的怎么做 + 例子 | `docs/ai/skills/` |
| 已知错误写法 | `docs/ai/anti-patterns.md` |
| 模块行为与不变量 | `docs/memory/<module>/` |
| 评审标准与严重度定义 | `docs/review/` |
| 流程与计划 | 顶层流程文档 |
| 可重复的验证 | 检查器 + 验证档案 |
| 临时任务状态 | `state/<task-slug>/`（gitignored） |

理由和上面所有条一样朴素：**一个事实的第二份拷贝，是第二个需要维持为真的东西。** 在根仓库重述子模块的文档、在 skill 里重述规则的正文、在钩子里打印规则文本——都是同一个错误的不同形态。钩子应该打印**指针和实时状态**，永不打印规则正文。
